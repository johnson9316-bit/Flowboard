## 1. 总体判断

**方向成立。** 「不自建会话/worktree/计划门禁状态机，改为复用一个已经把这些做完的执行后端，Taskfold 只做 Card、调度、人工决策和审计」是正确的取舍——`5-技术架构与选型.md:174` 自己就写过「换执行后端等于重写调度层」，越早把执行真相外置越好。§3 的四层职责表、§4.4 承认「上游是 Agent 面向的文本工具、不能直接当强类型协议」、§5 的「编码成功只到 review、不自动 done」都是清醒的判断。

**但有两个结构性风险，二者都会让当前方案在实施第一周就卡住：**

**风险一：把一个 LLM Agent 放在了状态机的真相路径上。** §4.4 要求 Bridge「每次同步必须产出并校验 DTO」，而 Bridge 的唯一事件通道是上游用 `openclaw gateway call chat.send --expect-final --timeout 30000` 打回来的 wake（`上游/src/wake-transport.ts:17-31`、`上游/src/wake-delivery-executor.ts:4-7`）——每次同步就是一次完整 LLM 回合，30 秒内要读 output、读 worktree、生成 DTO、写卡。更严重的是这条链路同时是治理漏洞：上游 delegate 模式的 wake 正文原文写着「You are the delegated decision-maker」「**APPROVE the plan directly if ALL of the following are true**」并直接给出可复制的 `agent_respond(..., approve=true, approval_rationale=...)`（`上游/src/session-notification-builders/waiting.ts:134-191`，我已逐行核实）。这段文本是注入到 Bridge 会话里的输入，与 Taskfold 的「禁止自批」提示词直接对抗，而上游对 `approve=true` 不做任何来源校验（`上游/src/actions/respond.ts:411-417`）。§7.2 的全部人工边界目前只是提示词约束，机制层是空的。

**风险二：「一波全交付」叠加「新旧路径共存但无按 Card 判据」。** 本仓已有三条会与新路径正面冲突的控制回路——父依赖门禁只认 `parent.status === "done"`（`本仓/src/backend/src/store-core.ts:810-827`）、dispatcher 对任何 `ready` 卡都会走 claim + worker prompt 旧路径（`本仓/src/backend/src/dispatcher.ts:265-269`、`:418-477`）、reconciler 每 15 秒按心跳判活并把静默超 30 分钟的卡打成 `blocked`（`本仓/src/backend/src/lifecycle.ts:95-99`、`本仓/src/backend/src/store-constants.ts:22-24`）。8.7 对这三处一字未提，而它们各自都足以让「等人工批准的 Card 保持 running」「父子 Card 串行推进」「新卡只走新路径」三条核心承诺失效。

结论：**方案的架构方向可以保留，但 §4（Bridge 契约）需要重构、§6（调度）需要补齐支点定义、§8（一波交付）不可行。**

## 2. 必须改的问题

按「不改就做不出来 / 会出数据或安全事故」排序，语义重复的已合并。

### M1. Bridge 的宿主形态与投递路由未定义 —— 这是第 0 号前置，不解决后面全部作废

**问题.** 整份方案建立在「存在一个只挂 `agent_*` 工具的 Bridge Agent 会话」之上，但全文 312 行没有一处说明这个会话由哪个进程、用哪个 API 创建，工具集由谁决定。而上游在 spawn 之前会强制校验「可信投递路由」：route 必须能解析出真实聊天 provider，`system` 路由被明确排除，只有 `oneShotCliRun` 或 sessionKey 含 `:cron:` 才豁免，否则直接返回硬错误并且**不启动任何会话**。

**取证.** `上游/src/async-launch-route.ts:15-58`（`isIntentionalNonUserContext` 只认 `oneShotCliRun` 与 `:cron:`；否则返回 `kind:"error"`，文案含 "No coding session was started."）；`上游/src/tools/agent-launch-resolution.ts:347-353`（error 直接 return）；`上游/src/session-manager.ts:557-559`（第二道 `throw`）；`上游/src/session-route.ts:10-25`（`KNOWN_SESSION_ROUTE_PROVIDERS` 全是聊天渠道）、`:134-146`（要求 `agent:` 前缀后出现已知 provider）、`:225-227`（system 不算 direct）。本仓 `本仓/src/backend/src/dispatcher.ts:115-119` 产出的 `agent:<agentId>:subagent:taskfold-<board>-<card>` 只有 4 段，`parseSessionConversationRef` 的循环根本不会执行，必然解析失败退化为 system。另：wake 投递依赖 `openclaw` CLI 在 Gateway 的 PATH 中（`上游/src/wake-delivery-executor.ts:137-141`），§7.1 第 4 条只校验了编码 CLI。

**怎么改.**
1. 在 §4 之前新增 §3.2「Bridge 宿主会话与投递路由」，三条路径二选一并写死：(a) 在 `~/.openclaw/openclaw.json` 配一个专用 bridge agent，`tools.alsoAllow` 挂 `taskfold_*` 与 `agent_*`（宿主确实支持按 agent 的工具白名单：`node_modules/openclaw/dist/types.openclaw-CXjMEWAQ.d.ts:652` 的 `tools?: AgentToolsConfig`、`types.tools-CBCgJD1K.d.ts:315-322`；Taskfold 的 43 个工具全部标 `optional:true`，需要 allowlist 命中才挂载），Taskfold 用 `card.agentId` 定向 `subagent.run`；(b) 以 `:cron:` 形态的 sessionKey 运行 Bridge；(c) 走 `oneShotCliRun` 的 CLI 调用。
2. 无论选哪条，都必须**预置一个可路由的投递渠道**（`fallbackChannel` 或 `agentChannels[repoRoot]`，一个真实 Telegram/Discord 目标，仅作为上游生命周期投递位，不作为审批入口），并在 §7.1 增加两条校验：「Bridge 工具可达」「路由可解析」「`openclaw` CLI 在 Gateway PATH 可执行」。
3. §9 的「不采用 Code Agent 审批通知」改为「不采用其按钮审批，但必须保留其投递路由作为启动前置条件」。同时在 §7.1 明确**禁止**为 Bridge 的 workspaceDir 配置 `agentChannels` 映射——`上游/src/tools/agent-sessions.ts:51` 会据此按 originChannel 静默过滤会话列表。
4. 这条必须以真实 Spike 结论落地（`ctx.deliveryContext` 是否被 OpenClaw 为 subagent run 注入，属仓库外行为，只能实测），**Spike 通过前不要展开 §4~§6 的实现**。

### M2. 治理只写在提示词里：批准 = 交出全部权限，而机制层完全没有兜底

**问题.** 三件事叠加，使 §7.2「Bridge 不得自行批准计划、自动合并、自动创建 PR」在当前设计下不成立：

1. **批准即放权。** `approve=true` 命中待批计划时执行 `session.switchPermissionMode("bypassPermissions")` 并注入「Exit plan mode immediately and implement the changes with full permissions. Do not ask for further confirmation.」；auto-resume 时配置直接写 `permissionMode: "bypassPermissions"`。上游自己的 wake 文案就写着「Permission mode: plan → will switch to bypassPermissions on approval」，而本仓 `openclaw.plugin.json` 的 `configContracts.dangerousFlags` 把 `permissionMode=bypassPermissions` 标为危险配置。取证：`上游/src/actions/respond.ts:134-135`、`:511-516`、`:326`；`上游/src/session-notification-builders/waiting.ts:136`。也就是说**批准之后不会再有任何权限审批型的「需处理」事件**，编码 Agent 可以做计划之外的任意操作：读 Taskfold 的明文 SQLite、读 `~/.claude.json`（上游自己就读它取 mcpServers，`上游/src/config.ts:38-48`）、`git push`（`上游/src/worktree-merge.ts:104-116`）。§7 全章（229-259 行）对「批准之后」零约束。
2. **delegate 的上游 wake 正文命令 Bridge 自批**（见第 1 节取证），且 idle timeout 后还会再催一次（`上游/src/session-lifecycle-service.ts:383-407` 的 `[DELEGATED PLAN APPROVAL REMINDER]`）。上游对审批来源不做校验。真正禁止自批的是 `plan_approval="ask"`，但 ask 的按钮回调只在 telegram/discord 注册（`上游/index.ts:292-293`），Taskfold 收不到。
3. **`agent_merge`/`agent_pr` 也是 Bridge 手上的工具，repo policy 拦不住。** `policy=manual` 只让 `allowedActions.merge/pr=false` 用于按钮可见性（`上游/src/repo-policy.ts:94-102`），而 `上游/src/tools/agent-merge.ts:179-186` 只在 `pr-required` 时拒绝、`上游/src/tools/agent-pr.ts:554-555` 只在 `never-pr` 时拒绝。
4. **`agent_goal_*` 是一条绕过全部治理的旁路，却被列进了 §4.1 允许工具表。** GoalController 的 `permissionMode` 默认 `bypassPermissions`（`上游/src/goal-controller.ts:441`）、硬编码 `worktreeStrategy: "off"` 并注释「Goal loops intentionally own terminal handling and disable worktree flows」（`:540-541`，即**直接改基线工作区**）、遇到 `pendingPlanApproval` 直接 `executeRespond({approve:true, userInitiated:false})` 自动批准（`:816-828`、`:884-892`）；`agent_goal_launch` 参数里也没有 `worktree_strategy`（`上游/src/tools/goal-launch.ts:33-60`）。这同时打破 §4.2 的三条固定策略和 §7.2 的两条硬规则。

**怎么改.**
1. **把人工确认下沉到机制层：按 action 裁剪 Bridge 的工具装载。** §4.1 表格增加一列「工具装载矩阵」：同步类 bridge run 只装 `agent_output`/`agent_worktree_status`（**根本没有** respond/merge/pr/cleanup 工具）；批准、合并、PR、清理各自用一次性的、只带对应单个工具的 bridge run，且只在人工点击后由 Gateway 发起。
2. `approve=true` 的调用参数必须携带 Taskfold 侧的审批 `auditEventId` + 计划内容哈希 + `planVersion`，缺任一即拒绝调用——这就是 §2.2「审阅证据」的可校验落地形式（目前 §4.4 只有 `sourceExcerptHash`，只能证明「见过某段文本」）。
3. §4.2 补 `allowed_tools`（`agent_launch` 支持该参数，`上游/src/tools/agent-launch.ts:102`），按 Profile 收窄；§7 新增「批准后的爆炸半径」小节：UI 审批界面必须明示「批准 = 该会话后续无门禁」；system prompt + allowed_tools 层面禁止访问 Taskfold 数据目录与凭据文件；§7.1 校验目标仓库不含 Taskfold 自身数据目录；`agent_merge` 固定 `strategy=merge`、`push=false`、`delete_branch=false`（推送是独立人工动作）；base 分支白名单，受保护分支用 `pr-required` 而非靠约定。
4. **把 `agent_goal_*` 从 §4.1 移除**，改为「本波不启用」，成本投影与它解绑。若确实要用，单列一节说明它绕过计划门禁与 worktree 隔离，并限制到专用仓库/专用 Profile。
5. §决策表的 delegate 语义描述要更正（现在写的「bridge 必须完整阅读计划，但不能自行批准」不是上游语义），否则后续实现者会按错误语义验收。

### M3. 与本仓三条既有控制回路正面冲突，文档一字未提改造

这三条各自独立、各自足以让核心承诺失效，必须在 8.7 里点名要改的文件。

**(a) 父依赖门禁只认 `done`，与「不自动 done」互斥 → §6 的串行链条永远走不动。**
`本仓/src/backend/src/store-core.ts:810-827`：目标状态为 ready/running/review/done 时，`!parents.every(p => p.status === "done")` 即抛 `card dependencies are not done.`；`:1145-1177` 的 `dependencyTargetStatus` 在 parents 未全 done 时把卡压回 `todo`。而 8.7:193 规定「无论编码 Agent 如何报告成功，Taskfold 都不得自动进入 done」，8.7:215-216 又要求「所有必需子 Card 到达 review 或 blocked 后，父 Card 才汇总」。叠加结果：前一环停在 review，后一环被压在 todo，整条 planner→implementer→tester→reviewer→integrator 链在没人逐环手工点 done 的情况下无法推进，gate 5 验不过。更冲突的是 `本仓/src/backend/src/store-workflow.ts:748-770` 的 `decompose` 默认 `completeParent !== false` 会直接完成父 Card——现有语义是「父拆完即完成、子才解锁」，与 8.7 要求的「父保持未完成、等子到 review 再汇总」正好相反。
**改法**：在 §6 之前定义「依赖满足」的新语义（建议：parent 处于 `review` 或 `done` 即视为满足；或阶段推进不复用 parent 链、单独建阶段依赖），并点名要改 `store-core.ts` 的 `assertActiveStatusAllowed`、`dependencyTargetStatus`、以及 `decompose` 的 `completeParent` 默认行为，补单测「parent 停在 review 时 child 可启动」。

**(b) 没有按 Card 的路径判据 → 任意一次 dispatch 会把 Code Agent Card 拉回旧路径。**
`TaskfoldAutomation`（`本仓/src/contract/index.ts:329-344`）没有任何执行路径字段；dispatcher 候选筛选只看 `status === "ready"`（`dispatcher.ts:265-269`），命中即 claim + `buildWorkerPrompt`（含 claim token 与 `taskfold_complete` 协议，`worker-prompt.ts:230-244`）+ 建受管 worktree。触发入口有五个且全部对外开放：`taskfold.cards.dispatch`/`dispatchWithOptions`、dashboard actionVerb `dispatch`（`openclaw.plugin.json:26-38`）、`taskfold_dispatch` 工具（`:73`）、CLI（`cli.ts:388-403`）、`taskfold.cards.execution.start`（`card-execution.ts:274-333`）。`card.agentId` 不能充当判据——dispatcher 只用它算 owner 和 sessionKey，不改变 prompt 与 claim 协议。
**改法**：§3.1/§4.3 增加持久化路径判据（`automation.executionPath: "code-agent" | "legacy-subagent"`，创建时确定、不可静默改写），并列出必须加拒绝分支的六处：`dispatcher.selectStartableCards`、`store.claim/dispatch`、`card-execution.startTaskfoldCardExecution`、`taskfold_dispatch`、dashboard actionVerb、CLI。gate 6 落成自动化断言（给一张 code-agent Card 跑 dispatch，断言不产生 claim/worktree/subagent run），不靠人工冒烟。顺带交代 `workspace-access.ts:90-94` 的 `TASKFOLD_REQUIRED_WORKER_TOOLS` 在新路径下如何处置。

**(c) 判活证据只有本地心跳 → 「等人工」会被判死，还可能删掉 Code Agent 的 worktree。**
`本仓/src/backend/src/lifecycle.ts:95-99` 用 `taskfoldLastActivityAt`（= max(claim.lastHeartbeatAt, execution.updatedAt, card.updatedAt)，`store-card-helpers.ts:418-424`）判 live/stale/abandoned，20 分钟 stale + 10 分钟宽限即 abandoned → `targetStatus="blocked"`；reconciler 每 15 秒跑一次（`reconciler.ts:32`），`finishOrphanedRun`（`:119-137`）会 `finishExecutionForRun({outcome:"failed"})` 并调 `cleanupTaskfoldRunWorktree`，后者按 `metadata.automation.workspace.path` 无条件 `removeIfLossless`（`dispatcher-workspace.ts:36-42`）。`store.ts:92-119` 还会在 claim 过期时把 running 卡改 blocked 并 `failureCount+1`。而 8.7:103-104 明令新路径不用 heartbeat，8.7:188 又要求等人工时保持 running。
注意这里有条件性：只要 Bridge 持续同步写卡（刷新 `lastSyncedAt`）就会刷新为 live，且 `lifecycle.ts:85` 要求 `claimsRunning(card) && cardSessionKey(card)` 才判定——所以真正的问题是**两种走法文档都没交代**：复用 `execution/sessionKey` 则会被误判为 blocked；完全不写 execution 则 lifecycle 永远 `unlinked`、卡片状态无法收敛，而 `本仓/README.md:31-42` 承诺的「不管有没有人打开看板都收敛」也随之失效。
**改法**：§7.3 新增「控制回路改造」小节：定义新路径的存活证据（`lastSyncedAt` + `externalStatus`）与同步节奏（周期、退避、连续 N 次不可确认后写 `external_state_unknown` 并标需处理）；引入 `waitingForHuman` 状态位使 abandoned 判定不生效（等人工不等于无活动）；点名 `lifecycle.ts` / `reconciler.ts` / `store.dispatch` 需按路径分支；**显式禁止把 Code Agent 的 worktree 路径写入 `metadata.automation.workspace`**，或给 `cleanupTaskfoldRunWorktree` 加 owner 判别。

### M4. `writeScope` 全文未定义 —— §6 整个并发模型和 gate 5 的唯一支点缺失，且没有任何互斥设施可复用

**问题.** `writeScope` 是并发键（`repository + baseBranch + writeScope`）、Profile 默认值、并行/串行判定、启动前合法性校验、gate 5 的共同支点，8.7 里出现六处（`:149`、`:203`、`:207`、`:217`、`:221`、`:239`、`:274`），**没有任何一处定义它的数据形态、由谁产出、如何校验「合法」、以及「重叠」的判定算法**。需求目录全文 grep 只命中 8.7 自身，本仓源码 grep `writeScope` 零命中。
两个必然卡住的点：(1) 「无法判断时默认串行」没有判定入口，实现者写不出这个判定；(2) §6:202-203 规定 Profile 带「默认 writeScope」，于是 §2.3:75 走 implementer 的简单 Card 全部继承同一个默认值 → 并发键完全相同 → 按 `:217` 仍判重叠而串行，§1:20-21 承诺的「允许安全的并行」在最常见路径上失效。
更根本的是**互斥设施不存在**：现有 CAS 是「card id + expectedRevision」的单卡准入（`store-workflow.ts:75-140`，注释「the database, not this process, decides who won」），dispatcher 容量约束是 per-ownerId 的粗粒度计数（`dispatcher.ts:244-284`），索引只有 board/status、session、claim_owner。两张不同 Card、同仓同分支、writeScope 重叠，在现有任何一层都不会被拦住。文档也没说这条规则实现在哪一层。

**怎么改.**
1. §6 之前新增「writeScope 规范」：取值 = 仓库相对路径 glob 列表（含排除项）；规范化算法；重叠判定（前缀/glob 交集，任一方声明 `**` 视为全仓独占）；lockfile、生成文件、共享配置的共享白名单策略；跨目录重构场景的处理；**未声明时拒绝启动 mutable run**（而非默默串行，否则并行能力形同虚设）；谁产出（planner 或用户显式确认）、何时固化（启动前，且批准后不可变）。

### M8. worktree 与 Git 基线的失控面：无配额、无 GC、无盘点，合并会 stash 主仓库，冲突会自动派生一个全权限会话

**问题（五条，同一主题）.**
1. **manual 策略下 worktree 永不进入 resolved，上游 GC 不触发.** 只有 resolved（merged/released/dismissed/no_change）之后 7 天才回收（`上游/src/session-maintenance-service.ts:13`、`:104-120`；`上游/src/application/session-view.ts:85`）。manual 的本意就是不自动解决，所以用户不点合并/PR/丢弃，worktree 与 `agent/*` 分支就永久堆积；唯一的空间保护是创建前检查剩余 ≥100MB（`上游/src/worktree-repo.ts:155-158`）。§7.3 只写「不重复启动」，全文无配额、GC、盘点，也没说 Card 删除/归档时 worktree 怎么办（Card 一删，关联断裂，worktree 成孤儿）。
2. **manual 策略下上游不产生任何 worktree 待决事件.** `上游/src/session-worktree-action-service.ts:114-117`：`if (!strategy || strategy==="off" || strategy==="manual") return { kind:"skip", ... }`——既不发用户通知也不 wake orchestrator，worktree lifecycle 停在 provisioned。§5「worktree 待决」这一行**没有上游事件源**。
3. **合并会在主仓库 checkout base 并自动 stash 用户未提交改动.** `上游/src/worktree-merge.ts:161-207`（squash）与 `:213-249`、`:283-294`（rebase/ff）都在主仓库 `git checkout base` + `git stash push` + `stash pop`，pop 冲突时用户的未提交工作会留在冲突的 stash 里（`:197-205` 的 `stashPopConflict`）。对「本机开发主力仓库」这是很现实的伤害。而 §7.1 六条校验**没有一条涉及工作区是否干净、HEAD 基线或 submodule**（全文 grep `dirty`/`HEAD` = 0），`baseCommit` 只作为事后投影字段。这也让 `9-风险与取舍.md:18`「run 前记录 HEAD，出事可回退」这条最后防线在新路径上没有落点，`8.4:243`「Git dirty 默认拒绝」也悬空。

5. **squash 冲突时上游自动 spawn 一个 `bypassPermissions` 会话，且跑在主仓库根.** `上游/src/tools/agent-merge.ts:334-357`：`sessionManager.spawn({ workdir: effectiveWorkdir, name: \`${params.session}-conflict-resolver\`, permissionMode: "bypassPermissions", multiTurn: true, ... })`，而 `:168` `let effectiveWorkdir = originalWorkdir` —— 即**在主仓库根目录**跑一个未被 Taskfold 登记、无审计、无计划门禁、不占 §6 并发键与预算、但会占 maxSessions=20 配额的全权限会话。§5 也没有「合并失败 / rebase 冲突 / worktree 清理失败」的 Card 状态与 UI 动作（`上游/src/types.ts:22-32` 的 `SessionWorktreeState` 含 `merge_conflict_resolving`、`cleanup_failed`）。频率上：这只发生在 squash 路径（rebase 冲突走人工提示不 spawn），属**低频但完全不可见**。

**怎么改.**

2. §5 把「worktree 待决」标注为 **Taskfold 推断态**（依据：编码 run 终止 + `agent_worktree_status` 的 lifecycle/preserve/cleanupSafe），§4.1 明确 `agent_worktree_status` 是该状态唯一数据源并给出轮询触发点；说明 `agent_request_worktree_decision` 被有意排除的原因（按钮只投递到聊天渠道）。
3. §7.1 增加两条校验：启动前读取并持久化目标仓库的 HEAD / 分支 / dirty / submodule 状态（dirty 默认拒绝，可项目级显式放宽，并重新论证 `8.4:243` 在「worktree 由 Code Agent 拥有」前提下是维持、放宽还是作废）；校验 Code Agent 报告的 worktree 基线与 `baseCommit` 一致，不一致即拒绝合并/PR。启动时显式传 `worktree_base_branch` 并把实际 fork commit 记进 `baseCommit`；§6 补 base 漂移处置（合并前比对，漂移则要求 rebase 重测）。

- **idle timeout 是默认路径而非边缘情况.** 多轮会话每个 turn 结束都重置 idle 定时器，默认 `idleTimeoutMinutes=15`（`上游/src/session.ts:912-925`、`:363-370`；`上游/src/config.ts:145`），触发即 `kill("idle-timeout")` + `suspended:true`（`:968-970` → `session-state.ts:265` lifecycle="suspended"）。而「输出完计划等待人工批准」正是一个 turn 结束态——人吃个饭回来会话已被 kill；上游还会再发一次 delegate 催批 wake（又一次 LLM 回合）。§5 映射表把 killed 统一归到 blocked，没有 suspended 这一档。功能不算真坏（`上游/src/actions/respond.ts:60-63` + `:417-424` 会对被 idle kill 的待批会话 auto-resume，但那会重新 spawn、占 maxSessions 配额）。
  **改法**：§5 增加映射行「`killed`+`killReason=idle-timeout`（suspended）→ 保持 running + 需处理（可恢复）」；§7.3 写明恢复靠 `agent_respond` 的 auto-resume；§7.1 增加部署前置：`idleTimeoutMinutes` 已按人工审批 SLA（例如 8 小时）配置，否则拒绝启动或明确告警。

## 3. 没考虑到的地方（缺口清单）

按主题归组，每组说缺什么、补什么。M1–M8 已覆盖的不重复。

**状态机缺口**
- `external_state_unknown` 只有进入条件（`:176-178`），**没有出口**：无重试次数、无退避、无「连续 N 次校验成功后恢复」、无人工强制解绑。§5 映射表也没有这一行（Card 该在 running 还是 blocked 未定）。补：unknown 期间 Card 保持 running + 需处理并进独立诊断分组；退避重试 + 最大次数，达上限升级 blocked 并给出「强制解绑会话」人工动作（清关联、留档旧 sessionId、允许重新 launch）。
- unknown 下「终止」不可靠：成因可能正是 sessionId 无法校验，此时传给 `agent_kill` 的参数本身不可信。补：先用 `agent_sessions` 按 name+workdir 二次定位，终止后必须复核会话消失，未复核成功不得声称已终止。
- 父 Card 汇总没有定义：「必需子 Card」的「必需」全文无定义（现有 `TASKFOLD_LINK_TYPES`（`contract/index.ts:59-65`）只有 parent/child/blocks/blocked_by/relates_to，无必需/可选语义，也没说 planner 如何标注）；§5 映射表也没有父 Card 汇总行（子卡 blocked 时父卡进 review 还是 blocked？）。补：子 Card `required` 标记 + 汇总映射行 + 阻塞时的三个人工选项（重试 / 降级为可选 / 整体 blocked）。
- 递归深度只提了「要限制」（`:224-225`），只有「预算耗尽」有行为定义。补：深度计数口径（按 Card 父链）、超限行为（拒绝创建 + 标需处理）、预算自上而下的分摊规则；`parentRunId` 单值 + `dependsOnRunIds` 同层依赖装不下多层拆分。

**执行期权限与人工提示投递**
- 「执行期权限请求落到哪个 Card 状态」这个问题的答案是：**不会有权限请求**，因为批准已经把会话升级为 bypassPermissions。这必须在 §7 写明，否则实现者会去做一个永远不触发的状态分支。
- 三类带按钮的上游人工提示（repo policy 选择、ask 模式 Approve/Revise/Reject、worktree Merge/Open PR/Discard）走 directNotifications 且要求 direct route；没有 direct route 时代码明确「refusing text-only fallback because buttons would be lost」并报投递失败（`上游/src/wake-dispatcher.ts:296-306`、`:349-360`），回调只在 telegram/discord 注册。§2.2 必须补一句：这三类提示在本方案下**必须全部避免触发**（预置 repo policy、固定 plan_approval、固定 worktree_strategy），否则会静默投递失败或流到聊天渠道。
- wake 只是「催促去拉状态」的信号，不能当事件真相：30s 超时、4 次重试（2s→20s 退避）、失败后回落 `openclaw system event`（`上游/src/wake-dispatcher.ts:311-313`）。§8.1 gate 2 要把前提写清：Bridge 必须有稳定 sessionKey、必须在 30s 内产出 final、必须按 idempotencyKey / (session + planVersion) 幂等去重。
- **wake 路由在 launch 时由调用方 ctx 固化**（`上游/src/tools/agent-launch-resolution.ts:267-271`、`上游/src/tools/agent-launch.ts:270-274`），Gateway 重启后新 Bridge 会话的 sessionKey 变了，旧会话的 wake 仍投向旧路由——这是「卡在 unknown 永远没有下一次同步」的直接成因。§7.3 必须写明重启后如何重建通知通道，或声明轮询为唯一真相、wake 仅作加速。

**Revise / 上游调用细节**
- Revise 在上游不是参数，只有精确匹配的英文魔法字符串 + 两次调用这一条路径：`normalizePlanReplyDecision`（`上游/src/actions/respond.ts:66-72`）只接受去尾标点小写后等于 `revise`/`request changes`/`changes requested`，且要求 `lifecycle==="awaiting_plan_decision" && pendingPlanApproval && userInitiated`；命中后 `requestPlanDecisionChanges`（`:256-273`）**只改状态、不转发任何内容**，必须再发第二次 respond 才是真正的修改意见。未命中时静默退化为 revision feedback：`planDecisionVersion` 不递增、`approvalState` 仍 pending、旧审批 token 不失效。§2.2 要把两步协议写死，并规定 Bridge 必须校验第一步返回文本包含预期提示，否则视为 Revise 未生效。§4.4 的 `needsAttention.planVersion` 要说明它对应上游的 `planDecisionVersion`/`actionablePlanDecisionVersion`。
- **会话 name 必须显式传.** §4.2 启动输入清单里没有 name。省略时上游用 `generateSessionName(prompt)`：先 `replace(/[^a-z0-9\s-]/g," ")` 剔掉全部中文，再取前 3 个关键词，全空时返回字面量 `"session"`（`上游/src/format.ts:78-87`）——中文标题的 Card 会得到无意义甚至同名的会话。硬伤在寻址：所有按 ref 解析的工具在 idIndex 未命中时会回退 `getLatestPersistedByName`（挑最近创建的同名会话，`上游/src/session-store-queries.ts:22-52`、`:87-95`），一旦任何一处传 name 而非 id，就会操作到别的 Card 的会话；worktree 目录与分支名也派生自 name（`openclaw-worktree-<name>`、`agent/<name>`，`上游/src/worktree-lifecycle.ts:60-79`），`agent/session` 这种分支名对人工 review 毫无信息量。补：§4.2 要求显式传全局唯一 ASCII kebab-case name（如 `tf-<board>-<cardShortId>`）；§4.1 加约束「Bridge 对上游的所有 session 参数只允许传 `codeAgentSessionId`，禁止传 name」；`codeAgentSessionName` 仅作展示，不得作为寻址键。
- **`agent_launch` 没有任何关联元数据通道，返回纯文本且错误不置 `isError`.** 参数表（`上游/src/tools/agent-launch.ts:94-139`）只有 prompt/name/workdir/model/system_prompt/allowed_tools/resume_session_id/fork_session/force_new_session/permission_mode/plan_approval/harness/worktree_strategy/worktree_base_branch/worktree_pr_target_repo——没有 metadata/labels（传 agentId 会被 warn 后忽略，`:150-152`）；所有返回（成功、模型不合法、workdir 不存在、resume-first blocked、repo policy 待选、启动异常）都是同一个 `{content:[{type:"text"}]}` 形状且**全文件无 `isError`**，sessionId 只能从 `  ID: <uuid>` 这行正则抠出来（`上游/src/launch-summary.ts:62-63`）。补：§4.2 写清关联字段的落点（只能进 name 与 prompt 的固定 header 块——上游有 `Workdir:`/`Repo:` header 解析先例）；Taskfold 侧以自己生成的 `bridgeRunId` 为关联主键，`codeAgentSessionId` 视为「解析得到、可能失败」的外部值；§4.4 为启动结果单列 `BridgeLaunchResult` DTO，明确「解析不到 ID 即视为启动结果未知，必须先对账再决定是否重试，**禁止直接重发 `agent_launch`**」。

**harness 能力不对等**
三个 harness 的差异正好落在方案依赖的四件事上：`nativePlanArtifacts` 只有 codex 为 true（claude-code 是把 plan 模式最后一个 turn 的纯文本合成 PlanArtifact，`上游/src/harness/claude-code.ts:124-128`、`:238-250`；opencode 连合成都没有，`上游/src/harness/opencode.ts:760-763`）；**完整计划文件只对 claude-code 提取**（判定条件是 Write 工具 file_path 含 `/.claude/plans/`，`上游/src/session-turn-runtime.ts:61-65`），且只在运行时会话 + pendingPlanApproval 时拼进 `agent_output`——所以「Bridge 必须完整阅读计划」在 codex/opencode 上拿到的只是 turn 文本；worktrees 能力 codex 是 native-restore、其余 plugin-managed；completed 会话可恢复性只有 codex/opencode 具备；opencode 的 plan 模式是把所有 mutation 权限设为 deny（`上游/src/harness/opencode.ts:149-159`），语义与 Claude 的 ExitPlanMode 门禁不同。
补：§8.1 gate 1 按 harness 拆三组并逐项标注能力差异与降级行为；§4.4 增加 `planSource`（plan-file / turn-text / synthesized）与 `harnessCapabilities` 快照，让 UI 能显示「本 harness 无法提供完整计划文件」；§7.1 第 6 条把 OpenCode 的实验性限制具体化为可校验项（本地 opencode 版本 ≥1.16.2、provider auth、plan=deny-all 语义）。

**Profile / 调度模型**
- **Profile 无策略覆写字段.** §4.2 把 `permission_mode=plan`、`plan_approval=delegate`、`worktree_strategy=manual` 写成每次启动的固定值，而 §6 的 Profile 字段清单没有这三项的覆写位。结果：tester 跑一次测试、reviewer 读一次 diff 都要先出计划等人批准，并且都留下一个待人工决策清理的 worktree。父卡拆 5 个子卡就产生十几次无意义审批——用户会开始无脑点批准，人工门禁事实失效。上游支持逐次覆写（`上游/src/tools/agent-launch.ts:111-133` 三个参数都是可选）。补：Profile 加 `permissionMode`/`planApproval`/`worktreeStrategy` 三个字段并给默认矩阵（implementer = plan+用户批准+manual；tester/reviewer = 无计划门禁 + worktree off 或只读快照 + 结束即清理；planner = plan+用户批准+worktree off），§4.2 措辞改为「必须显式提供，取值来自 Profile，默认为…」。
- **Profile 没有存储落点.** 现有唯一相关物是 `board.orchestration.orchestratorProfile`——一个 120 字符以内的自由字符串（`contract/index.ts:391-396`、`store-normalizers.ts:193-203`），全仓无消费方；没有 Profile 表、版本或校验。补：新表 `taskfold_profiles`（主键 id+version，内容 JSON 白名单校验），board/card 只存 `activeProfileId`+version 引用；说明内置 Profile 是代码常量还是可编辑数据。
- **「生产执行入口默认禁用」没有开关落点.** `openclaw.plugin.json:223-227` 的 configSchema 是 `{type:object, additionalProperties:false, properties:{}}`——没有任何可用配置项且禁止未声明字段，代码里也没有读插件配置的地方。补：configSchema 增字段（如 `codeAgent.enabled`、`codeAgent.allowedBoardIds`）或改为项目级设置，并写明未开启时哪些 gateway 方法直接拒绝。
- **缺项目/仓库级并发上限.** `8.8:5` 明确要求「同项目/同仓库设置并发上限」，8.7 的最大并发挂在 Profile 上（`:202`）、额度挂在父调度 run 上（`:224`），没有项目/仓库级硬上限。

**tester / reviewer 执行环境**
「目标 branch 的受控快照或只读检查环境」是文档自造概念，上游没有对应能力：`WORKTREE_STRATEGIES` 只有 off/manual/ask/delegate/auto-merge/auto-pr（`上游/src/types.ts:77`），`createWorktree` 只能从主检出当前 HEAD 建 `agent/<name>` 分支或检出已存在分支，没有 base commit / start-point 参数（`上游/src/worktree-lifecycle.ts:60-148`、`上游/src/session-bootstrap.ts:314`）。而 git 不允许同一分支同时检出到两个 worktree，所以「给 implementer 的分支再开一个 worktree 给 tester」走不通；剩下的做法是让 tester 直接用 implementer 的 worktree（`worktree_strategy=off`），那就是 §6 规则 3 明令禁止的同 worktree 双 writer。
另外「每次前后检查 Git diff，出现非预期修改即记录协议违规、阻塞 Card」**没有排除集**——跑测试必然产生构建产物、缓存、依赖目录，有时更新 lockfile，按字面规则每次测试都会被判协议违规，tester Profile 首次真实运行即不可用，gate 5 这条验收也失去区分度。而 §3.1 又规定 worktree 只能由 Code Agent 创建拥有，Taskfold 自建快照目录需要显式例外。
补：把「受控快照」落成具体机制（建议 Taskfold 侧 `git worktree add --detach <path> <commit>` 生成只读快照，以 `workdir=<快照路径>, worktree_strategy=off` 启动 tester，并显式为快照开 §3.1 的例外、说明谁清理、配额多少）；或放弃独立 tester worktree，改为 implementer 自测 + reviewer 只读 diff 文本。「非预期修改」定义为「对 `.gitignore` 排除项之外的跟踪文件的修改」，给出可配置忽略清单（lockfile 是否算修改需显式取值）；gate 5 用例同时覆盖「真实越权修改被阻塞」和「测试副产物不被误判」。

**UI 缺口（比「加 10 个按钮」大）**
现有执行面板只有 5 个动作（prepare/start/inspect/steer/abort，`ui/src/main.ts:838/874/901/949/986`），而「回复/终止」这两个与 §5 同名的动作是浏览器**直连宿主方法**实现的：`:945-954` `gateway.request("sessions.steer", {key: sessionKey, message})`、`:973-991` `gateway.request("chat.abort", {sessionKey, runId})`，都把 `card.execution?.sessionKey` 当宿主 session 用。新路径的 session 属于 Code Agent，这两条必须整条重写走 Bridge，不是加按钮。另外 §6 规则 7 要求输出落 Card 评论，但 UI 里评论功能一个字都没有（`grep -c comment ui/src/main.ts ui/src/pages/projects/project-view.ts` 均为 0，后端 `gateway.ts:299` 有 `taskfold.cards.comment` 方法但无界面），审计视图与 worktree 摘要同样从零开始，都要塞进 `ui/src/main.ts`（1109 行）和 `ui/src/pages/projects/project-view.ts`（2253 行）。i18n 相对可控（缺键回退英文，`ui/src/i18n/lib/translate.ts:211-230`）。
补：§5 补一张 UI 动作矩阵（每个按钮 → gateway 方法 / 可用前置条件（含 unknown 时只允许刷新/摘要/终止）/ 二次确认 / 失败提示）；明确旧的 `sessions.steer`/`chat.abort` 直连方式在新路径下作废，新增 `taskfold.codeAgent.*` 方法承接；评论区与审计视图作为独立工作项列出，不要混在「10 个按钮」里估工。
另外 **`8.8:4` 明确要求的「项目级 Runs 视图」在 8.7 中完全没有对应物**（§5 只定义 Card 详情操作，全文无「项目页」），而 `8.4:97` 要求「`awaiting_human` 项必须在项目页和 Card 上显著可见，不依赖用户翻进详情」。补一节「项目级 Runs/需处理视图」（列：Card、Profile/harness、session、worktree、需处理原因、最后同步时间），并进 §8.2 验收。

**终端接管路径整体消失，无作废说明**
`4-执行调度与AI.md:156-163` 称接管是「这套设计里性价比最高的一环」；`7-数据与接口.md:238` 定义 `GET /runs/:id/takeover` 与 `resumable_session_id`；`14-OpenClaw技能策略.md:66` 把「人可在真实终端恢复或接管对应会话」列为进入 M2 的必测项；`1-规划评审.md:35` 把「真终端 resume 实测」写成决策 B 的放行门。8.7 全文 grep「接管」/「resume」= 0。补：给出接管映射（用会话标识给出可在真终端恢复的命令，或明确返回不可接管原因），或写明在 Agent SDK harness 下接管不再必要（claude-code harness 走 `@anthropic-ai/claude-agent-sdk` 并有 `interrupt?()`，`上游/src/harness/claude-code.ts:6`、`:38`，原来主张接管的技术前提已变）并**逐条作废** 7:238、8.4:145、14:66、1:35 的接管门。

**迁移与双路径共存 / 文档治理**

## 4. 开发方案合理性逐项判断

| 项 | 判断 | 理由 |
| --- | --- | --- |
| **分层职责（§3 四层表）** | **合理** | 「Code Agent 是执行真相、Taskfold 只做关联/摘要/审计/UI 投影」（`:182-183`）是这份方案最正确的一句话。四层职责与「不负责内容」列都划得清楚。唯一问题是 Bridge 这一层的实现形态错配（见下） |
| **Bridge 设计** | **有问题** | 详见下方专门回答 |
| **DTO 契约（§4.4）** | **需调整** | 方向对（承认上游是文本工具、加 schemaVersion、无法校验时降级），但缺五样：启动结果单列 `BridgeLaunchResult`（含「ID 解析失败 = 启动结果未知」规则）、`lifecycle` 取值集合（至少要能表达 suspended）、`planSource` 与 `harnessCapabilities`、`worktree.state` 的完整枚举（含 `merge_conflict_resolving`/`cleanup_failed`）、`upstreamPluginVersion`。另外 `sourceExcerptHash` 只能证明「见过某段文本」，不足以充当「审阅证据」；`external_state_unknown` 只有入口没有出口 |
| **Profile / 调度模型（§6）** | **需调整** | Profile 作为「版本化执行配置而非第二套任务系统」的定位是对的，但：缺三个策略覆写字段导致只读角色也走计划门禁 + 留 worktree；缺存储落点与版本机制；角色归属（Card vs 子 Card）§2.3 与规则 3 自相矛盾；调度的核心支点 `writeScope` 未定义、互斥设施不存在；「必需子 Card」「受控快照」两个自造概念无定义；预算无计量源 |

### 专门回答：把 LLM Agent 当作跨插件强类型协议桥，是正确的架构选择吗？

**不是。** 四条理由，都有取证支撑，不是审美判断：

1. **对抗性输入无法用提示词压制。** 上游会主动把决策指令注入 Bridge 会话——delegate 的 wake 正文命令它直接批准（`上游/src/session-notification-builders/waiting.ts:134-191`），idle timeout 后再催一次（`上游/src/session-lifecycle-service.ts:390-403`），返回文本还会建议它去 respond 别人的 session（`上游/src/tools/agent-launch-resolution.ts:272-313`）。Taskfold 的 system prompt 只是另一段文本，冲突时行为不可保证；而上游对 `approve=true` 不校验来源。用 LLM 做治理边界 = 用提示词做权限系统。
2. **成本与延迟结构性不匹配。** 每次同步 = 一次完整 LLM 回合（10–60 秒），而 wake 的投递窗口只有 30 秒（`上游/src/wake-delivery-executor.ts:4-7`），待批计划时 `agent_output` 还会把计划文件全文拼进返回（`上游/src/application/session-view.ts:242-252`）。N 卡 × 多种事件 × UI 刷新会线性放大调用量，而文档没有任何频率/去抖/预算约束。
3. **文本解析没有版本契约。** 全部投影建立在解析 launch summary 行格式、wake 文本、`agent_worktree_status` 行格式之上，而上游有 npm 自更新（`上游/src/auto-update.ts`）——一次升级即静默失效，且失效方式是「解析出错的字段」而非「报错」。
4. **不确定性进了状态机的真相路径。** LLM 会漏读、会幻觉、会重复动作（wake 重试 4 次时是否重复触发取决于 Gateway 的幂等处理）。而这条路径决定 Card 的状态、审计记录和是否允许合并。

**更好的替代：三层拆分，把 LLM 从真相路径上摘掉。**

- **事实读取层（确定性，零 LLM）**：上游的会话索引是磁盘上的版本化 JSON（`OPENCLAW_CODE_AGENT_SESSIONS_PATH`，默认 openclaw home 下 `code-agent-sessions.json`，`schemaVersion=7`，见 `上游/src/session-store-storage.ts:58-84`、`上游/src/session-store-normalization.ts:38`）。Taskfold 在 Gateway 进程内直接读它生成 `BridgeSessionProjection`（lifecycle / worktree / costUsd / pendingPlanApproval / approvalState / planDecisionVersion 全在里面），毫秒级、可测试、可版本校验。同时用 `agent_output(session=<id>)` 与 `agent_worktree_status(session=<id>)` 这两个**能按 ref 精确命中**的工具做交叉验证（注意 `agent_sessions` 不能按 session 查、默认 5 条、full 只覆盖 24h，只能当辅助）。
- **动作执行层（确定性 + 最小工具集）**：每个人工动作 = 一次一次性 bridge run，只装载该动作对应的**单个** `agent_*` 工具，全部参数由 Taskfold 生成，Bridge 不做任何判断（它只是一个「把参数递过去、把返回文本递回来」的通道）。`approve=true` 必须携带 Taskfold 的审批 auditEventId + 计划哈希 + planVersion。这样即使 Bridge 被上游文本诱导，它手上也没有可以滥用的工具。
- **语义摘要层（唯一的 LLM 用途）**：计划摘要、失败原因摘要、review findings 归纳。事件驱动 + 按 session 去抖 + 每卡与全局的次数/金额上限，产物只写进 `summary` 类字段，**不参与任何状态判定**。

**两点诚实的代价必须写进文档**：(a) 直读 `code-agent-sessions.json` 是对上游内部实现的耦合，与 §9「不采用私有源码导入、内部单例、未公开 Gateway API」的表态在精神上有张力——建议改写为「不导入私有源码、不依赖内部单例；只读取其磁盘上的版本化会话索引，并以 `schemaVersion` + 插件版本双重校验，schema 变化即降级 stale」。(b) 长期正解是向上游提 PR 增加结构化事件/查询接口（或注册 gateway method——上游目前只注册 tools，全仓 `registerGatewayMethod` 零命中），把 Bridge 降级为可选加速层。这应该在 8.7 里立项，而不是靠 LLM 桥长期代偿。

## 5. 交付节奏建议

「不拆分多期」不现实：M1 的 Spike 结论会决定 §4 是否整体重写，M3 的控制回路改造是后续每一期的地基，而 §6 的并行是唯一能造成数据损坏的能力。建议如下切分——**每期结束都有一个可用的东西，且下一期不会推翻上一期的数据模型**。

**第 0 期：可行性 Spike（不写产品代码，1 周内）**
- 内容：Bridge 宿主形态选定并实测（route 能否解析、工具能否挂载、`openclaw` CLI 是否在 Gateway PATH）；`agent_launch` → 解析返回文本拿到 sessionId → `agent_output`/`agent_worktree_status` 读回；直读 `code-agent-sessions.json` 生成一份 projection 的可行性；claude-code 完成后 completed 与 fork 行为实测；idle timeout 与 auto-resume 实测。
- Gate：一条可复现的命令能起一个真实 claude-code 会话，读回 lifecycle / pendingPlanApproval / costUsd，且证据（命令、环境、两个插件版本、真实 payload）写入 `本仓/VERIFICATION.md`。
- 为什么先做：这一条不通，§4~§6 全部作废；这一条的结论也决定 Bridge 是「协议桥」还是「摘要器」。

**第 1 期：单卡最小闭环（只 implementer、只 claude-code、单 active mutable run，不做并行）**
- 内容：路径判据字段 + 六处拒绝分支；控制回路按路径分支（存活证据、`waitingForHuman`、禁止误删 worktree）；独立 append-only 审计表 + 字段归属表 + 四处同步改动；`launching` CAS 准入；启动 / 同步 / 回复 / 批准（带审批凭据）/ 修订（两步协议）/ 终止 / 查看 worktree；按 action 裁剪的工具装载矩阵；入卡脱敏 pipeline。
- Gate：启动→计划→人工批准→执行→review 走通；Gateway 与 Taskfold 重启后恢复同一 session 投影且不重复启动；**等人工 2 小时后 Card 仍是 running + 需处理**（不被 reconciler 判死）；对 code-agent Card 调用旧 dispatch/execution.start/CLI/工具全部被拒（自动化断言）；每个人工动作都能在审计表里逐条查到 actor。
- 为什么这样切：控制回路 + 审计存储 + 路径判据是地基。不先做，后面每一期都是在往一个会被 reconciler 打死、审计会被静默挤掉的状态机上加功能。

**第 2 期：人工出口与 Git 安全面**
- 内容：合并 / PR / 丢弃 worktree（固定 `strategy=merge, push=false, delete_branch=false`）；合并冲突与清理失败的状态映射与 UI 动作；未登记 session（conflict-resolver）的发现与告警；启动前 HEAD/dirty/submodule 校验与 `baseCommit` 一致性校验；base 漂移处置；worktree 配额 + 三方对账盘点 + Card 归档/删除时的 worktree 归属；`external_state_unknown` 的退避与「强制解绑」；「退回修改」（fork + 会话链）。
- Gate：主仓库 dirty 时启动被拒并给出可操作指引；合并冲突不产生未登记的写入会话；盘点能列出三类孤儿；unknown 卡能通过退避恢复或人工解绑后重启。

**第 3 期：并发与 writeScope**
- 内容：writeScope 规范（形态、规范化、重叠算法、共享白名单、未声明拒绝启动）；store 层并发槽表（唯一索引 + 与 revision CAS 同事务）；项目/仓库级并发上限；成本账本（四级）与预算耗尽处置。
- Gate：不重叠并行 / 重叠串行 / 槽位在 run 结束与失联回收时正确释放 / 预算耗尽停止派发且不 kill 在跑的 run / 并发双击与双入口只产生一个会话。
- 为什么放这里：并行是唯一能造成数据损坏的能力（`9:19` 的原始判断是对的），必须等单卡闭环稳定、审计可信之后再开；同时这一期也是 `1-规划评审` 决策 C 需要正式改判的地方。

**第 4 期：多角色 Profile 与父子调度**
- 内容：Profile 表 + 版本 + 三个策略覆写字段；依赖语义改造（`store-core.ts` 三处）；子 Card `required` 标记 + 父 Card 汇总映射 + 递归深度与预算分摊；tester/reviewer 执行环境（快照机制或降级为只读 diff）+ 非预期修改的排除集；项目级 Runs/需处理视图；评论区与审计视图。
- Gate：§8.1 gate 5 的全部项 + 「parent 停在 review 时 child 可启动」+ 「测试副产物不被误判为协议违规」。

**第 5 期：多 harness**
- codex（可开放）→ opencode（实验性、非阻塞、UI 标注）。gate 1 按 harness 分列，opencode 冒烟结果仅作记录。
- 为什么最后：与主场景解耦，不该卡发布。

**生产入口开关**：第 1 期结束后即可对**白名单看板**开放（配置项 `codeAgent.enabled` + `allowedBoardIds`），而不是等七条 gate 全过。全量开放的门槛设在第 3 期结束（并发安全成立之后）。
