# flowboard 规划评审

> 评审日期：2026-07-27。依据 v0.8 规划文本完成桌面审阅，未对 OpenClaw、gsd-core 或代码仓进行实测。本文件的“需修正”结论优先于从原文机械拆分出的旧表述。

## 结论

产品方向有明确差异化：以 GSD 产物为骨架、用看板和调度补齐 gsd-core 的空白。已确认当前只服务个人开发者，并采用 TypeScript + Node。问题集中在“实现前提尚未证实”和“产品模型没有收敛”，不是功能点不足。当前不能把 M1-M2 当作连续开发任务；应先完成验证门和最小模型决策。

## P0：开工前必须处理

| 问题 | 证据与影响 | 需修正 |
|---|---|---|
| 决策门相互矛盾 | 原文称 A/B/C 全部阻塞开工，又称 B 可在 `AgentRunner` 后延后；C1 已是推荐默认值。 | 只有 A（语言）阻塞 M1 代码。B 是 M2 前的验证门，C 直接采用 C1，C2 留 M3。 |
| MCP 里程碑矛盾 | 架构预留写 M1 暴露 MCP server，路线图又把 MCP server 放 M4。 | M1 不做 MCP；M4 才交付可供外部 agent 使用的 MCP server。 |
| 数据真相冲突 | 数据设计是“按实体分权”，风险表却写“SQLite 为准”。 | 改为“每个实体一个真相源”：GSD 产物在文件，flowboard 原生实体与运行账本在 SQLite；禁止双向权威。 |
| GSD 与工作项映射未定义 | Phase/Plan/Wave 来自文件，WorkItem 在 SQLite；表结构没有 phase 投影或稳定关联键。 | 在 M4 前定义 `project_id + phase_id + plan_id`、story 到 phase、task 到 plan 的映射、创建者和同步方向；否则跨项目聚合、run 归属和度量无法可信。 |
| 执行安全模型缺失 | 调度层可运行具备 Read/Edit/Bash 的开发 agent；`coding-agent` 还要求为 Git 修改使用隔离 worktree。 | 增加 workspace 白名单、启动前 Git 状态检查、隔离 worktree 与基线提交记录、命令与网络权限策略、预算阈值、密钥文件排除、审计与人工批准规则。 |
| 小团队承诺没有运行条件 | 已确认目标用户为个人开发者；本机 SQLite、无同步/共享部署/权限不构成当前缺口。 | 小团队不列入 M1-M3 承诺；若未来恢复该方向，需先补共享部署、身份与并发写入方案。 |

## P1：进入对应里程碑前处理

| 问题 | 影响 | 建议 |
|---|---|---|
| story 状态与 Phase 状态重复 | `ready` 后进入 phase，但 story 又有 `doing/verifying/done`；状态样例还缺少 ready 后的转换并引用未声明的 `rejected/deferred`。 | 指定 story 的交付状态是否由关联 phase 投影；补全合法转换、拒绝/暂缓状态、异常流与验收完成的唯一判定。 |
| 数据模型约束不足 | `actor` 的自由字符串无法可靠区分人、agent 与系统；comments 的 MD 与表存储不清；links 无方向和循环约束；run 的 phase/plan 不是外键。 | 先画 ERD 与状态机，再写表。个人版采用 `actor_type + actor_id`；定义评论正文唯一落点和关联完整性。 |
| 长会话恢复语义未定义 | Gateway 重启、CLI 退出、网络失败时，run 可能永久显示 running。 | 设计持久队列、幂等启动键、启动时 reconciliation、超时/重试/终止语义与 orphan run 的人工恢复流程。 |
| M1/M2 范围过大 | M1 若同时改造宿主依赖、重写架构和新增 GSD 功能，会失去复制 Workboard 的价值；此前 M2 同时含 gsd-core 内化、索引、跨项目和调度。 | M1 只交付可安装的 Workboard 复制插件；M2 只做多项目、项目设置和项目资料；GSD 只读投影与单 repo、单隔离 worktree run 的 OpenClaw 执行适配移至 M4。 |
| 实时能力被未验证假设绑住 | WebSocket 是否能穿过 frame 尚未验证。 | M1 验收允许轮询；WebSocket 通过 M1.0 后才列为必达，失败时登记反代或 SSE 方案。 |
| AI 辅助边界不完整 | 独立模式的管理型 AI provider、凭证、成本、隐私、提示注入和失败处理未定义。 | M4 前先写 Provider 选择、数据最小化、写操作审批、重试与成本上限；未完成前只交付不调用模型的功能。 |
| 配置与格式演进缺失 | YAML、SQLite、`.planning/` 都会演进，但没有 schema 版本、迁移、回滚和兼容策略。 | 为配置、数据库和投影格式分别定义版本字段、迁移器、备份与 `doctor` 检查。 |

## 已确认决策与阶段门

1. **已确认**：采用 TypeScript + Node；Flowboard 是 OpenClaw 插件，插件 ID 为 `flowboard`、显示名称为 `Flowboard`。现有 Python 资产只保留设计参考。
2. B：默认采用 OpenClaw 的 `coding-agent` 能力，但不是无条件定案。完成 Gateway 连接、后台执行、事件归集、隔离 worktree、项目 MCP 并存和真终端 resume 实测后才允许进入 M2；失败则评估裸 spawn，不直接上 Agent SDK。
3. C：M2 固定“同 repo 单 active run + 单隔离 worktree”。M3 才评估多 worktree 并行与合并策略，不以 wave 假设换取数据损坏风险。
4. `.planning/phases/**/runs/` 在验证上游归档行为前不得写入；先落 `<FLOWBOARD_HOME>/runs/`，验证通过后再迁移。
5. **2026-07-28 已确认**：M1 完整复制 OpenClaw 官方 Workboard 功能层作为 `flowboard` 插件，而不是自写 React 看板或独立服务。复制范围是 Workboard 插件、契约包、Workboard UI 页面/状态/样式及其直接依赖；保留其既有宿主依赖、Lit + Vite 和插件规范。

## 缺失但应补充的管理信息

- 目标指标：M1 采用率或试用项目数、M2 单次 run 成功率和人工介入率的基线，不只记录技术指标。
- 责任与节奏：每个里程碑要有负责人、预计工期、复盘日期和“未达标则降级/停止”的条件。
- 用户研究：至少找 3 个现有 GSD 使用者验证“跨项目看板 + 调度”是否比终端工作流更有价值。
- 发布与支持：npm 包命名、兼容的 OpenClaw/Node/CLI 版本、升级回滚、错误日志脱敏、最小隐私声明。
- 质量策略：核心状态机、reindex、队列恢复、权限拦截和 GSD 格式兼容需有自动化测试；插件端需保留真实宿主的烟测。
