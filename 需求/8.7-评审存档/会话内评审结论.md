# 8.7 方案评审

## 总体判断

**方向成立，但文档目前处于「架构意图清晰、落地地基未验证」的状态，按现在这版直接开工会在第一周撞墙。**

三点结构性问题：

1. **最上游的一步没验证过**：`agent_launch` 在 spawn 前强制要求一个可解析的聊天投递路由，而 Taskfold 现有的 sessionKey 形态过不了这道门。这是唯一的真 blocker。
2. **所有治理承诺（不自动批准/不自动合并/不自动 done）目前都只是写给 LLM 的提示词，没有一条有机制保障**——而上游会主动往 Bridge 会话里注入「你可以直接批准」的指令，方向正好相反。
3. **文档只写了「Taskfold 该怎么做」，没写「Taskfold 现有的控制回路会怎么做」**。现有 reconciler 每 15 秒判活一次，新路径又禁用 heartbeat，结果是所有新 Card 会在 30 分钟内被自动打成 `blocked`。

方案的优点也要说清：职责边界表（§3）划得准，「Code Agent 是执行真相、Taskfold 只存投影」这个定位是对的；不自动 `done`、worktree 人工决策、拒绝启动而非降级这几条决策都是正确的保守选择；§4.4 意识到「自然语言输出不能当强类型协议」并给出 DTO，这个直觉是对的（只是解法选错了）。

## 一、必须改的问题

### 1. Bridge 宿主会话与路由 —— 唯一 blocker

`agent_launch` 启动异步会话前调 `resolveRequiredAsyncLaunchRoute`，要求能解析出 direct route（provider 必须是 telegram/discord/slack 等已知聊天渠道），只有 `oneShotCliRun` 或 sessionKey 含 `:cron:` 才豁免；否则硬错误 `did not provide a trustworthy lifecycle delivery route ... No coding session was started`。

- [async-launch-route.ts:25-58](tpm/benchmarks/openclaw-code-agent/src/async-launch-route.ts#L25-L58)、[session-route.ts:134-146](tpm/benchmarks/openclaw-code-agent/src/session-route.ts#L134-L146)（`agent:` 前缀后必须出现已知 provider，否则退化成 `system`）、[session-manager.ts:557](tpm/benchmarks/openclaw-code-agent/src/session-manager.ts#L557) 第二道 throw
- Taskfold 侧 [dispatcher.ts:115-120](src/backend/src/dispatcher.ts#L115-L120) 产出的是 `agent:<agentId>:subagent:taskfold-<board>-<card>`，`subagent` 不在已知 provider 列表里

§7.1 的 6 条启动前校验完全没有这一项，而 §9 还把 Code Agent 自带的聊天通知列为「不采用」——等于把唯一能过门的机制排除了。

**改法**：在 §4.2 之前新增「Bridge 宿主会话与路由」一节，三条路选定一条并写清代价：(a) 配 `agentChannels[repoRoot]` 或 `fallbackChannel` 指向一个专用聊天目标，仅作生命周期投递位、不作审批入口（须同步关掉上游的用户可见审批通知）；(b) Bridge 以含 `:cron:` 的 sessionKey 运行；(c) 走 `oneShotCliRun`。同时把「路由可解析」加进 §7.1。**这一条必须先做 spike 实测**，因为它决定后面所有设计。

### 2. 治理边界要下沉到机制层，不能靠提示词

§7.2「Bridge 不得自行批准计划、自动合并、自动创建 PR」目前零保障：

- **`plan_approval=delegate` 的语义与文档描述相反。** 上游把 delegate 定义为「orchestrator 就是被委派的决策者」，wake 正文 STEP 3 明确写 `APPROVE the plan directly if ALL of the following are true`，并给出现成调用 `agent_respond(..., approve=true, approval_rationale=...)`；只有 `ask` 模式的 wake 才写 `DO NOT approve this plan yourself`。见 [waiting.ts:137-216](tpm/benchmarks/openclaw-code-agent/src/session-notification-builders/waiting.ts#L137-L216)。而 `executeRespond` 对 `approve=true` 只检查 approvalState 是否被拒，**不检查审批来源**（[respond.ts:412-471](tpm/benchmarks/openclaw-code-agent/src/actions/respond.ts#L412-L471)）。这段 wake 文本是注入到 Bridge 会话的输入，与 Taskfold 的 system prompt 直接对抗——Bridge 是 LLM，冲突时行为不可保证。
- **`approve=true` 不是「同意这个计划」，是「把会话永久升级为 `bypassPermissions`」**：[respond.ts:511-516](tpm/benchmarks/openclaw-code-agent/src/actions/respond.ts#L511-L516) 调 `switchPermissionMode("bypassPermissions")` 并注入前缀 `Exit plan mode immediately and implement the changes with full permissions. Do not ask for further confirmation.`。上游自己的 plugin manifest 把这个值标为 `dangerousFlags`。批准之后编码 Agent 的所有工具调用再无任何门禁——§7 对这个爆炸半径没有任何补偿设计。
- `agent_merge` / `agent_pr` / `agent_worktree_cleanup` 都在 Bridge 手上；repo policy=`manual` 只影响按钮可见性，不拦工具调用（只有 `pr-required` 拦 merge、`never-pr` 拦 PR）。
- `ask` 模式的 Approve/Revise/Reject 按钮回调**只在 telegram/discord 注册**，Taskfold 收不到。

**改法**：在 §4.1 表格增加一列「工具装载矩阵」——同步类 bridge run 只装 `agent_sessions`/`agent_output`/`agent_worktree_status`（根本没有 respond/merge/pr 工具）；审批、合并、PR 各自用一次性、只带单个工具的 bridge run，且只在人工点击后由 Gateway 发起。`approve=true` 的调用必须携带 Taskfold 侧的审批审计 ID，Bridge 侧用代码而非提示词校验。并在决策表里更正 delegate 的真实语义。

### 3. 现有控制回路会自动杀掉新路径的所有 Card

Taskfold 的判活证据是 `max(claim.lastHeartbeatAt, execution.updatedAt, card.updatedAt)`：超 20 分钟 stale，再过 10 分钟宽限就是 abandoned，reconciler 每 15 秒跑一次并 `finishExecutionForRun(outcome:"failed")` 把卡推到 `blocked`；`store.dispatch` 还会在 claim 过期时把 running 卡改 blocked 并 `failureCount+1`。

- [reconciler.ts:32](src/backend/src/reconciler.ts#L32)、[lifecycle.ts:41,80-100,173-175](src/backend/src/lifecycle.ts#L80-L100)、[store-constants.ts:22-24](src/backend/src/store-constants.ts#L22-L24)、[store-card-helpers.ts:418-424](src/backend/src/store-card-helpers.ts#L418-L424)、[store.ts:92-120](src/backend/src/store.ts#L92-L120)

8.7 明令新路径不用 heartbeat，又要求等待人工审批期间「保持 running」。人吃个饭回来，卡片已经被判死。更危险的是 `finishOrphanedRun` 会调 `cleanupTaskfoldRunWorktree`，按 `metadata.automation.workspace.path` 无条件 `removeIfLossless`——如果 §4.3 的 `worktreeSummary` 很自然地落到这个字段，Taskfold 就会删掉「只能由 Code Agent 拥有和清理」的 worktree。

叠加上游的 **15 分钟默认 idle timeout**（[session.ts:913-925](tpm/benchmarks/openclaw-code-agent/src/session.ts#L913-L925)、[config.ts:54](tpm/benchmarks/openclaw-code-agent/src/config.ts#L54)）：等审批超过 15 分钟，上游会 `kill("idle-timeout")` 并置 suspended。§5 会把它归到「人工终止/会话失败」→ blocked，但真实语义是可恢复的挂起。

**改法**：新增「控制回路改造」一节 —— `lastSyncedAt`/`externalStatus` 定义为新路径的存活证据并规定刷新时机；`waitingForHuman` 是合法稳定态，abandoned 判定对其不生效；lifecycle/reconciler/store.dispatch 按路径分支；**明令禁止把 Code Agent 的 worktree 路径写入 `metadata.automation.workspace`**；§7.1 增加一条「上游 `idleTimeoutMinutes` 已按人工审批时长（如 8 小时）配置」，否则拒绝启动。

### 4. 「不自动 done」与现有依赖门禁互斥

现有实现里，卡片只要有 parent，进入 ready/running/review/done 都会被硬校验拦住，条件是**所有 parent 的 status === 'done'**；依赖驱动的自动晋升也只在 parents 全 done 时才推到 ready，否则压回 todo。

- [store-core.ts:815-831](src/backend/src/store-core.ts#L815-L831)（`throw new Error("card dependencies are not done.")`）、[store-core.ts:1157-1177](src/backend/src/store-core.ts#L1157-L1177)

而 8.7 规定编码成功只到 `review`、`done` 必须人工，§6(3) 又要求 planner→implementer→tester→reviewer→integrator 按依赖串行。两者叠加：前一环停在 review，后一环被压在 todo，**整条专业 Agent 链条在没人逐环手工点 done 的情况下无法推进**，gate 5 验不过。

**改法**：在 8.7 里定义依赖满足的新语义（建议「parent 处于 review 或 done 即视为满足」，或阶段推进不复用 parent 依赖链），并点名要改 `assertActiveStatusAllowed`、`dependencyTargetStatus`、decompose 的 `completeParent` 默认行为。

### 5. 新旧路径没有按 Card 的开关点

现有代码没有任何路径判据字段（`TaskfoldCard`/`TaskfoldExecution`/`TaskfoldAutomation` 里都没有），dispatcher 的候选筛选只看 `status === "ready"`，命中即 claim + `buildWorkerPrompt`（含 claim token 和 `taskfold_complete` 指令）+ `subagent.run` + 创建受管 worktree。而触发入口有五个且全部对外开放：`taskfold.cards.dispatch`/`dispatchWithOptions`、dashboard actionVerb `dispatch`、`taskfold_dispatch` 工具、CLI、`taskfold.cards.execution.start`。

- [dispatcher.ts:265-270](src/backend/src/dispatcher.ts#L265-L270)、[worker-prompt.ts:230-244](src/backend/src/worker-prompt.ts#L230-L244)、[gateway-helpers.ts:120-127](src/backend/src/gateway-helpers.ts#L120-L127)、[openclaw.plugin.json:26-39,73](openclaw.plugin.json)

只要一张 Code Agent Card 落到 ready，任何一次 dispatch 就会给它起一个旧路径 run，直接违反 §7.2，gate 6 不成立。

**改法**：新增持久化路径判据（如 `automation.executionPath: "code-agent" | "legacy-subagent"`，创建时确定、不可静默改写），并列出六处必须加拒绝分支。**gate 6 应落成自动化断言**（给一张 code-agent Card 跑 dispatch，断言不产生 claim/worktree/subagent run），而不是人工冒烟。顺带说明 [workspace-access.ts:90-94](src/backend/src/workspace-access.ts#L90-L94) 的 `TASKFOLD_REQUIRED_WORKER_TOOLS` 在新路径下怎么处置。

### 6. §4.3 的字段没有落点，写进去会「看似成功、读出来消失」

两类障碍：

- **run 级字段无承载实体**：数据库没有 runs 表（[sqlite-store.ts:160-449](src/backend/src/sqlite-store.ts#L160-L449) 全部 CREATE TABLE 里没有），run 记录是 `card.metadata.attempts` 数组（上限 30，预算不足时**最先被丢**），attempt 结构装不下 `parentRunId`/`dependsOnRunIds`/`writeScope`/`bridgeRunId`。
- **不是「JSON blob 随便加字段」**：`normalizeAutomation` 与 `removeUndefinedAutomationFields` 是显式白名单（[store-normalizers.ts:559-627](src/backend/src/store-normalizers.ts#L559-L627)、[:1384-1410](src/backend/src/store-normalizers.ts#L1384-L1410)），未列出的 key 每次写入被直接丢掉，metadata 同理。每个新字段要同步改四处：contract 类型、normalizers 白名单、sqlite 列/表、UI 类型。且 `SCHEMA_VERSION=7` 的迁移只支持加法式（无重命名、无回填）。

### 7. 审计在现有数据模型里无处安放

`TaskfoldEvent` 只有 id/kind/at/fromStatus/toStatus/milestone/sessionKey/runId——**没有 actor、没有 detail/payload**；`TASKFOLD_EVENT_KINDS` 是封闭枚举，不在枚举内的 kind 归一化时**静默丢弃**；events 上限 50、comments 50、proof 40、workerLogs 40，metadata 总量超 24KB 时按固定顺序丢最早的。更关键的是持久化层每次整卡写入都是 `DELETE FROM <子表> WHERE card_id = ?` 后重插——**审计在存储层不是 append-only**。

- [contract/index.ts:160-170](src/contract/index.ts#L160-L170)、[store-normalizers.ts:711-723](src/backend/src/store-normalizers.ts#L711-L723)、[store-constants.ts:9-24](src/backend/src/store-constants.ts#L9-L24)、[store-normalizers.ts:1520-1562](src/backend/src/store-normalizers.ts#L1520-L1562)、[sqlite-store.ts:1120-1129](src/backend/src/sqlite-store.ts#L1120-L1129)

一个多 Agent 父卡跑半天，早期审计（恰恰是「谁批准了什么」）会被挤掉，§8.2 的「审计可恢复」和「防篡改」都不成立。

**改法**：新增独立 append-only 表（`taskfold_audit_events`：只 INSERT，带单调序号与 prev_hash 链式校验），Card 只留最近 N 条 id 引用；计划全文/diff/测试输出走附件或外部文件 + 摘要入卡；把 §6 规则 7 的「落入 Card」明确成「摘要入卡 + 全文入附件/审计表」。

## 二、把 LLM 当强类型协议桥 —— 这是错的，有更好的解

§4.4 意识到问题（自然语言不能当协议）但解法方向反了：让 LLM 产出 DTO，等于把不确定性放在关键路径上，还要为它付成本。

**成本与延迟**：唯一的事件通道是上游用 `openclaw gateway call chat.send --expect-final --timeout 30000` 把 wake 打回编排会话（[wake-transport.ts:17-31](tpm/benchmarks/openclaw-code-agent/src/wake-transport.ts#L17-L31)、[wake-delivery-executor.ts:3-7](tpm/benchmarks/openclaw-code-agent/src/wake-delivery-executor.ts#L3-L7)：30 秒超时、4 次重试）。每个 wake 就是一次完整 LLM 回合。§4.4 要求「每次同步」都由它产出 DTO，而文档全篇没有触发策略、频率、去抖、并发上限、成本上限。N 个运行中 Card ×（计划就绪／每回合完成／worktree 待决／3 小时提醒／idle 提醒／UI 每次点刷新）线性放大；`agent_output` 在待批计划时还会把整个计划文件**原文**拼进返回文本。而 Bridge 要在 30 秒窗口内读 output、读 worktree、生成 DTO、写 Card。

**更好的解 —— 拆成两条路径**：

1. **状态投影走非 LLM 直读**。上游的会话索引就是磁盘上的版本化 JSON（`OPENCLAW_CODE_AGENT_SESSIONS_PATH`，默认 openclaw home 下 `code-agent-sessions.json`，`schemaVersion=7`，见 [session-store-storage.ts:58-84](tpm/benchmarks/openclaw-code-agent/src/session-store-storage.ts#L58-L84)、[session-store-normalization.ts:38](tpm/benchmarks/openclaw-code-agent/src/session-store-normalization.ts#L38)）。Taskfold 可以在 Gateway 进程内直接读出 lifecycle / worktree / cost / pendingPlanApproval 生成 `BridgeSessionProjection`——**零 LLM 成本、毫秒级、无幻觉**。代价是依赖一个未公开的磁盘格式（有 schemaVersion，可做兼容校验并在版本不符时降级到 LLM 路径）。
2. **动作路径也可以不走 LLM**。上游除 `registerTool` 外还注册了 slash 命令（[index.ts:26-36](tpm/benchmarks/openclaw-code-agent/index.ts#L26-L36)），且 [commands/agent-respond.ts](tpm/benchmarks/openclaw-code-agent/src/commands/agent-respond.ts) 里 `userInitiated: true` 是**硬编码**的（注释：`Command is always user-initiated`）。走命令通道，「用户真的说了这句话」在结构上成立；走 tool 通道时 `userInitiated` 只是一个 LLM 自己填的字段。
3. **只有真正需要自然语言理解的场景**（计划摘要、失败原因摘要）才走 LLM Bridge，且必须事件驱动、按 session 去抖、带每卡与全局的次数/金额上限。文档应明确写「UI 刷新不得触发 LLM 同步」。

§9 那句「不采用未公开 Gateway API」把这两条路都排除了。这个排除的代价是把整个系统的可靠性押在 LLM 的格式稳定性上——不划算，建议改成「优先直读，LLM 仅作降级与摘要」。

## 三、没考虑到的地方

**writeScope 完全未定义。** 它是并发控制的唯一支点（并发键、Profile 默认值、并行/串行判定、启动校验、gate 5 共六处依赖），但全文没有定义数据形态（路径 glob？目录前缀？模块名？）、谁产出、如何校验、**重叠如何判定**。全仓检索确认这个词只在 8.7 出现。而且 Profile 自带的默认 writeScope 对所有 implementer Card 相同，按 §6 的并发键仍判定重叠而串行——§1 承诺的「允许安全的并行」在最常见路径上失效。跨目录重构、生成文件、lockfile、共享配置这类天然重叠场景零策略。建议：取值为仓库相对 glob 列表 + 明确的交集算法 + lockfile/生成文件白名单 + **未声明时拒绝启动 mutable run 而非默默串行**。

**并发键没有可复用的实现层。** 现有 CAS（`claimExecution`）是「按 card id + expectedRevision」的单卡准入，只保证同一张卡不被两个进程同时启动；dispatcher 的容量约束是 per-ownerId 的粗粒度计数；索引只有 board/status、session/run、claim_owner。两张不同 Card、同仓库同分支、writeScope 重叠，现有任何一层都不拦（[store-workflow.ts:75-137](src/backend/src/store-workflow.ts#L75-L137)、[dispatcher.ts:244-284](src/backend/src/dispatcher.ts#L244-L284)）。建议 store 层新增并发槽表（规范化并发键 + 唯一索引 + 插入即领取，与 revision CAS 同一事务），并定义拿不到槽位时的行为与释放时机。

**worktree 生命周期无回收。** 上游只对 resolved（merged/released/dismissed/no_change）的 worktree 排 7 天 GC；`manual` 的本意就是不自动解决，所以用户不点合并/丢弃就永久堆积。唯一空间保护是创建前检查剩余 ≥100MB（[worktree-repo.ts:92-106](tpm/benchmarks/openclaw-code-agent/src/worktree-repo.ts#L92-L106)、[session-maintenance-service.ts:104-120](tpm/benchmarks/openclaw-code-agent/src/session-maintenance-service.ts#L104-L120)）。Card 删除/归档后关联断裂，worktree 变孤儿。tester 快照会放大数量。建议：配额上限（落到 §7.1）+ Gateway 周期盘点（`git worktree list` ∪ 会话索引 ∪ Taskfold 关联三方对账，输出三类差异清单）+ Card 归档前强制 worktree 决定。

**合并冲突路径缺失。** §5 只映射了「合并或 PR 完成」，没有合并失败/冲突/清理失败；UI 动作清单也没有冲突入口。而 squash 冲突时上游会自动 spawn 一个 `<session>-conflict-resolver` 会话，`permissionMode: bypassPermissions`，**workdir 是主仓库根目录而不是隔离 worktree**（[agent-merge.ts:334-359](tpm/benchmarks/openclaw-code-agent/src/tools/agent-merge.ts#L334-L359)、[:168](tpm/benchmarks/openclaw-code-agent/src/tools/agent-merge.ts#L168)）。这个会话不在 §4.3 的关联里、无审计、无审批，直接击穿 §7.2。rebase 冲突（更常见）只返回人工提示。频率低但完全不可见。`SessionWorktreeState` 里已有 `merge_conflict_resolving`、`cleanup_failed` 两个状态可用。

**预算没有可用计量源。** `agent_stats` 无参数、只返回全局计数与平均时长，**拿到了 `totalCostUsd` 却根本没打印**；per-session 成本只出现在会话列表文本里；`agent_sessions` 没有按 session id 过滤的参数，默认只给最近 5 条、`full=true` 也只覆盖 24 小时（超 24 小时的长跑 Card 直接消失）；上游配置里没有任何 budget 字段。见 [agent-stats.ts:9-24](tpm/benchmarks/openclaw-code-agent/src/tools/agent-stats.ts#L9-L24)、[format.ts:198-230](tpm/benchmarks/openclaw-code-agent/src/format.ts#L198-L230)、[session-view.ts:76-77](tpm/benchmarks/openclaw-code-agent/src/application/session-view.ts#L76-L77)。建议自建账本：每 turn 结束上游把 `total_cost_usd` 写进 `session.costUsd`，Taskfold 从会话索引按 sessionId 累加到 Card/父卡/项目/全局四级。§6 规则 6 还漏了最关键一问：**预算耗尽时已在跑的 run 怎么办**（建议不 kill，禁止新 turn 与新 run，标记需处理）。

**「退回修改」做不出来。** §2.1 把它列为 review 后四个出口之一，但 §4.1 无工具映射、§5 无 review→running 转移。而默认 harness claude-code 的 completed 会话**不可 resume**——`canResumeCompletedSession` 只认 codex-app-server/opencode-server（[session-resume.ts:40-62](tpm/benchmarks/openclaw-code-agent/src/session-resume.ts#L40-L62)），唯一出路是 `agent_launch(fork_session=true)` 产生新 session id，与 §4.3 单值 `codeAgentSessionId` 及「不得重复 agent_launch」冲突。建议：`codeAgentSessionId` 改成会话链 `sessionLineage[]` + `forkedFromSessionId`，把「不创建重复会话」重述为「不并发创建两个活跃会话」，gate 3 按 harness 分列验收。

**重复启动保护键与 Card 无关。** 上游的 resume-first 去重键是 `workdir + originSessionKey`，不是 cardId。同仓库并行子 Card 在「已有可恢复会话」时第二次 launch 会被 `blocked`，返回文本还会**主动建议 Bridge 去 `agent_respond(session='<第一个 Card 的会话>')`**（[agent-launch-resolution.ts:266-311](tpm/benchmarks/openclaw-code-agent/src/tools/agent-launch-resolution.ts#L266-L311)）。让 LLM 读这段建议，很可能把 B 卡的指令发进 A 卡的会话。必须显式传 `force_new_session=true`（8.7 里一次都没出现），Bridge 的 prompt 必须禁止采纳工具返回文本里的 session 建议，`blocked` 文案必须映射为明确错误而非让 LLM 自由决策。

**`agent_goal_*` 与三条默认策略全冲突。** GoalController 的 `permissionMode` 默认 `bypassPermissions`，`spawnTaskSession` 里**硬编码 `worktreeStrategy: "off"`**（注释写明 goal loop 故意禁用 worktree 流程，即直接改基线工作区），遇到 pendingPlanApproval 直接 `executeRespond(approve:true, userInitiated:false)` 自动批准；`agent_goal_launch` 没有 `worktree_strategy` 参数（[goal-controller.ts:441,539-542,816-828](tpm/benchmarks/openclaw-code-agent/src/goal-controller.ts#L539-L542)）。建议本波直接从 §4.1 移除，成本投影与它解绑。

**批准后的爆炸半径**：没有文件系统沙箱阻止编码 Agent 读 Taskfold 的 SQLite 库、`~/.claude.json`（上游自己就会读它取 mcpServers）、其它项目、SSH key；CLI 已登录意味着能花钱、能 `git push`（[worktree-merge.ts:105-118](tpm/benchmarks/openclaw-code-agent/src/worktree-merge.ts#L105-L118)，`agent_merge` 的 `delete_branch` 默认 true）。建议：`allowed_tools` 按 Profile 收窄、`agent_merge` 一律不传 push、base 分支白名单、policy 用 `pr-required` 而不是靠约定、§7.1 校验目标仓库不含 Taskfold 自身数据目录。

**脱敏不够**：现有 [card-redaction.ts](src/backend/src/card-redaction.ts) 只处理 claim token，而 §6 规则 7 要求全量 Agent 输出入卡，密钥会写进数据库并经 dashboard 暴露。

**其他缺口**（各一两句即可补进文档）：`external_state_unknown` 没有出口条件、没有 Card 状态映射，且 session id 不可信时「终止」如何保证真的终止；`baseCommit` 与 worktree 真实 fork 点不一致，且 merge 会 checkout base 并自动 stash 用户未提交改动；tester/reviewer 的「受控快照」上游无对应能力，**git 不允许同一分支双 worktree**，且前后 diff 检查会被构建产物/缓存/lockfile 必然误判；会话 name 由英文关键词生成，中文 Card 全部退化为 `session`，导致按名命中错卡与分支撞名；Profile 与「执行入口默认禁用」没有存储落点（插件 configSchema 是封闭的）；上游有 npm 自更新能力，8.7 只锁了调研 commit，没有运行时契约锁定（建议启动时校验工具名清单）；「先检查已保存关联」是 TOCTOU，应复用现有 revision CAS 与 `idempotencyKey`（[dispatcher.ts:472](src/backend/src/dispatcher.ts#L472) 已有这套原语）。

## 五、交付节奏：建议分四期

「不拆分多期」+ 7 条含三 harness 冒烟和多 Agent 并行的 gate = 一个长期不可用的大爆炸发布。而且第一条 blocker 未验证前，后面所有设计都可能推翻重做。建议：

**第 0 期 · 地基 Spike（1–2 天，只写探针代码，不改产品）**
必须实测三件事，每件都可能改变整体设计：① Bridge 宿主会话能否让 `agent_launch` 过路由门（三条路各试）；② Gateway 内直读 `code-agent-sessions.json` 能否稳定产出 `BridgeSessionProjection`；③ claude-code 会话 completed 后的真实可操作面（能否避免自然 completed、fork 的实际代价）。
**Gate 0**：三份实测记录。②失败才回退 LLM Bridge。

**第 1 期 · 单卡闭环（最小可验证）**
范围：单 Card、单 harness（claude-code）、单 repo 单 active mutable run、**无并行、无子 Card、无 Profile 体系**。含：路径判据字段 + 六处拒绝分支、控制回路改造、直读投影、审批/合并/PR 的工具装载矩阵、独立 append-only 审计表、idle timeout 配置校验。
**Gate 1**：计划→人工批准→执行→review→人工合并 全程闭环；Gateway/Taskfold 重启后恢复投影不重复启动；自动化断言「code-agent Card 跑 dispatch 不产生 claim/worktree/subagent run」；等待人工 40 分钟不被判 blocked。

**第 2 期 · 多 Agent 与并发**
Profile 存储与 harness 覆写、父子 Card、依赖语义改造（review 视为满足）、writeScope 规范 + 并发槽表、成本账本四级汇总、worktree 配额与三方盘点。
**Gate 2**：原 gate 5 全部项 + 重叠 writeScope 串行的自动化验证。

**第 3 期 · Codex；第 4 期 · OpenCode**
按 harness 差异化验收，**OpenCode 标记实验性且不作为生产入口的放行条件**。

这样切的理由：第 1 期就能交付「从 Card 启动本机 Claude 开发」这个 §1 的首要场景，用户当天可用；并发与多 Agent 是风险最高、定义最不清的部分，独立成期才有时间把 writeScope 想清楚；三个 harness 的能力差异（计划产物、worktree、恢复能力都不对等）本来就不该同期验收。

## 三、其他实质增量

**合并会伤到主仓库的未提交工作。** squash/rebase/ff 三条路径都在**主仓库**做 `git checkout base` + `git stash push` + `stash pop`（[worktree-merge.ts:161-207](tpm/benchmarks/openclaw-code-agent/src/worktree-merge.ts#L161-L207)），pop 冲突时用户的未提交改动留在冲突的 stash 里。而 §7.1 六条校验**没有一条涉及工作区是否干净或 HEAD 基线**（全文 grep `dirty`/`HEAD` = 0）——这让 [9-风险与取舍.md:18](需求/9-风险与取舍.md)「run 前记录 HEAD，出事可回退」和 8.4:243「Git dirty 默认拒绝」两条防线在新路径上都没有落点。**建议 §4.1 的 `agent_merge` 固定 `strategy=merge`（禁 squash）、`push=false`、`delete_branch=false`** —— 这同时绕开了那个 bypassPermissions 的 conflict-resolver 路径。

**worktree 的 fork 点不是 baseBranch，是主检出的当前 HEAD**（[worktree-lifecycle.ts:124-138](tpm/benchmarks/openclaw-code-agent/src/worktree-lifecycle.ts#L124-L138)），`worktree_base_branch` 只影响后续 merge/PR 目标。§6 并发键里的 `baseBranch` 描述的隔离语义与实际 fork 点不是一回事。

**wake 路由在 launch 时被调用方 ctx 固化**（[agent-launch-resolution.ts:267-271](tpm/benchmarks/openclaw-code-agent/src/tools/agent-launch-resolution.ts#L267-L271)）。Gateway 重启后新 Bridge 会话的 sessionKey 变了，旧会话的 wake 仍投向旧路由——**这是「卡在 `external_state_unknown` 后永远没有下一次同步」的直接成因**。§7.3 必须写明重启后如何重建通知通道，或干脆声明轮询为唯一真相、wake 仅作加速。

**会话 name 是个寻址硬伤，不只是显示问题。** `generateSessionName` 先 `replace(/[^a-z0-9\s-]/g," ")` 剔掉全部中文，全空时返回字面量 `"session"`（[format.ts:78-87](tpm/benchmarks/openclaw-code-agent/src/format.ts#L78-L87)）。要命的是所有按 ref 解析的工具在 id 未命中时会回退 `getLatestPersistedByName`——**挑最近创建的同名会话**（[session-store-queries.ts:22-52](tpm/benchmarks/openclaw-code-agent/src/session-store-queries.ts#L22-L52)）。中文 Card 全部叫 `session`，一旦任何一处传 name 而非 id 就会操作到别的 Card 的会话；worktree 目录与分支也派生自 name（`agent/session`）。**§4.2 必须要求显式传全局唯一 ASCII name（如 `tf-<board>-<cardShortId>`），§4.1 加约束「Bridge 只允许传 sessionId，禁止传 name」。**

**`agent_launch` 的返回不可靠**：无 metadata/labels 参数（传 agentId 会被 warn 后忽略），所有返回（成功、模型不合法、workdir 不存在、resume-first blocked、启动异常）都是同一个 text 形状且**全文件没有 `isError`**，sessionId 只能从 `  ID: <uuid>` 这行正则抠出来（[launch-summary.ts:62-63](tpm/benchmarks/openclaw-code-agent/src/launch-summary.ts#L62-L63)）。必须写死一条规则：**解析不到 ID = 启动结果未知，必须先对账再决定，禁止直接重发 `agent_launch`**。

**Revise 是两步协议 + 精确英文魔法字符串。** [respond.ts:66-72](tpm/benchmarks/openclaw-code-agent/src/actions/respond.ts#L66-L72) 只接受去尾标点小写后等于 `revise`/`request changes`/`changes requested`；命中后**只改状态、不转发任何内容**，必须再发第二次 respond 才是真正的修改意见；未命中时静默退化为普通反馈（planVersion 不递增、审批 token 不失效）。§2.2 的「先提交明确的 Revise 决定，再转发具体修改意见」方向对但必须写死协议细节和校验。顺带：**§2.2「用户拒绝计划时调 agent_kill」是多余的——上游 reject 内部已经 kill。**

**「Bridge 必须完整阅读计划」只对 claude-code 成立。** 完整计划文件的提取条件是 Write 工具的 file_path 含 `/.claude/plans/`（[session-turn-runtime.ts:61-65](tpm/benchmarks/openclaw-code-agent/src/session-turn-runtime.ts#L61-L65)），`nativePlanArtifacts` 只有 codex 为 true，opencode 连合成 PlanArtifact 都没有。gate 1 的三 harness 同构假设在最核心的一环就不成立。

**UI 的两个同名动作现在是浏览器直连宿主。** [ui/src/main.ts:945-954](ui/src/main.ts#L945-L954) 的「回复」是 `gateway.request("sessions.steer", {key: sessionKey, ...})`，[:973-991](ui/src/main.ts#L973-L991) 的「终止」是 `chat.abort`，都把 `card.execution?.sessionKey` 当宿主 session 用。新路径的 session 属于 Code Agent，**这两条必须整条重写走 Bridge，不是加按钮**。而 §6 规则 7 要求输出落 Card 评论——**评论界面根本不存在**（后端 `gateway.ts:299` 有 `taskfold.cards.comment` 方法，UI 里零实现）。

**Profile 与「默认禁用」都没有存储落点。** 现有唯一相关物是 `board.orchestration.orchestratorProfile`——一个 120 字符以内的自由字符串、全仓无消费方；[openclaw.plugin.json](openclaw.plugin.json) 的 configSchema 是 `{type:object, additionalProperties:false, properties:{}}`，**没有任何可用配置项且禁止未声明字段**。

**tester 快照有具体做法**：`git worktree add --detach <path> <commit>` + `worktree_strategy=off`（git 不允许同分支双 worktree，所以「给 implementer 分支再开一个 worktree」走不通）。「非预期修改」应定义为「对 `.gitignore` 排除项之外的跟踪文件的修改」，并给可配置忽略清单——否则 tester 首次真实运行就会因构建产物被判协议违规。

**gate 的证据落点已有现成做法**：[VERIFICATION.md:100-103](VERIFICATION.md#L100-L103) 记的教训正是「测试用 fixture 断言了宿主并不具备的契约，所以测试通过而代码从未能工作」，而 `test/host-contract.test.ts` 已经在把真实 payload 固化为契约测试——照搬即可。

## 四、分期方案的修正

综合结论把我的四期细化成五期，两处调整我认同：

- **并发/writeScope 独立成第 3 期**（我原来和 Profile/父子调度放在一起）。理由站得住：并行是唯一能造成数据损坏的能力，[9-风险与取舍.md:19](需求/9-风险与取舍.md) 的原始判断（同 repo 单 active run）是对的，必须等单卡闭环稳定、审计可信之后再开。这一期也正是 `1-规划评审` 决策 C 需要正式改判的地方。
- **人工出口与 Git 安全面独立成第 2 期**（合并/PR/丢弃 + dirty 校验 + worktree 盘点 + unknown 出口 + 退回修改）。
- **生产入口不必等七条 gate 全过**：第 1 期结束即可对**白名单看板**开放（`codeAgent.enabled` + `allowedBoardIds`），全量开放的门槛设在第 3 期结束。这比原文档的「全 gate 前禁用」务实得多。

第 0 期（Spike）和第 1 期（单卡闭环）与我上一版一致；第 4 期多角色 Profile、第 5 期多 harness（codex 可开放、opencode 非阻塞仅记录）。
