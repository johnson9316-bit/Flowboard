## 1. 产品定位

**GSDbord** —— **GSD 流程的原生看板与协作层**。

> **核心逻辑是 GSD 流程，看板只是载体。**
> 上游：[open-gsd/gsd-core](https://github.com/open-gsd/gsd-core)（MIT，TypeScript）—— GSD = **Git. Ship. Done.**，一套 spec-driven 的五阶段开发框架。

一句话差异化：

> gsd-core 明确声明「**No database, no server, no external dependencies**」，状态全在 `.planning/` 的 MD + JSON 里，**且完全没有 UI**。
> **GSDbord 填的正是它主动不做的那一块。**

### 1.0 GSDbord 的价值边界

| gsd-core 已有 | gsd-core 没有 = **GSDbord 的价值** |
|--------------|--------------------------------|
| 五阶段循环、编排、meta-prompting、fresh-context 子 agent | **可视化** —— 一个 UI 都没有 |
| `.planning/` 文件状态、lockfile 原子写 | **跨项目聚合** —— 每 repo 一份 `.planning/`，10 个 repo 就是 10 份孤岛 |
| `STATE.md` 里的 metrics 字段 | **度量图表** —— 无历史、无 CFD、无燃尽 |
| 单人 + agent 的工作流 | **多人协作** —— 无 assignee、无团队视图、无负载 |
| `REQUIREMENTS.md` 平铺文档 | **需求池 / 优先级排序 / 缺陷跟踪 / 时间盒迭代** |
| 阶段循环由人在终端里逐步喊命令推进 | **执行调度**（v0.8 新增）—— 多会话排队、可观察、可接管、可复盘；每日巡检（§8.4–§8.6） |

> 这个差异化比「local-first + AI」硬得多，并且**彻底回答了「为什么不用 Plane」**：Plane 根本不认识 GSD 的阶段与产物。

五条设计主线：

1. **GSD 流程为骨架** —— 内建工作流就是 GSD 的阶段循环，不是通用 kanban 套一层壳（§3.5、§4.1）。
2. **本地优先（local-first）** —— 数据落在本机 `.planning/`，无云依赖，Git 可版本化。
3. **AI 一等公民** —— 需求拆解、优先级建议、验收标准生成、进展播报，内建而非外挂。
4. **★ 调度而非执行**（v0.8 新增）—— GSDbord **自己不写代码**，只把开发执行变成可排队 / 可观察 / 可验证 / 可接管的异步流程；真实执行者是 Claude CLI / codex / opencode 等专业开发 agent（§8.4）。
5. **独立核心 + 宿主适配器** —— 核心可独立运行；OpenClaw 是**当前唯一分发渠道**，不是运行时归属（§1.1）。

### 1.1 形态与分发路线（⚠️ v0.8 收敛：**只做 OpenClaw**）

**终局形态：独立软件。当前唯一在做的插件宿主：OpenClaw。Hermes 退场。**

```
        ┌──────────── gsdbord core（独立、零宿主依赖）────────────┐
        │  domain · workflow · planning · orchestrator · metrics  │
        └─────────────────────────────────────────────────────────┘
              ↓ 两个对外契约（§9.5-1）
        ┌─────────────────────┬───────────────────────────┐
        │  HTTP（localhost）   │  MCP server（agent 工具）  │
        └─────────────────────┴───────────────────────────┘
           ↓                ↓             ↓          ↓
        OpenClaw       gsdbord serve    VS Code   Codex / 其他
        [唯一在做]      [终局形态]      [以后]     [纯 MCP]
                            ↑
              ┌─────────────┴──────────────┐
              │  执行调度层（§8.4）：驱动     │
              │  Claude CLI / codex /       │
              │  opencode 真正干活           │
              └────────────────────────────┘
```

**Hermes 退场的连带后果**（三条都是推翻，不是调整）：

| 原结论 | 现状 | 影响 |
|--------|------|------|
| §9.9「抄 Hermes 官方 kanban 插件」 | ❌ **作废** | 那 3917 行 IIFE 绑死 `window.__HERMES_PLUGIN_SDK__`，OpenClaw 里根本加载不了。**看板 UI 得自己写**（§9.2） |
| §10.5「路线甲：Hermes 原生 IIFE」 | ❌ **作废** | standalone 成唯一前端路线，Vite 从「可延后」变成「M1 必做」 |
| §9.1「后端必须 Python，是宿主决定的」 | ⚠️ **依据消失** | 那个「宿主」是 Hermes。OpenClaw **只支持 JS/TS**。语言决策重开，见 §9.1 |

> **这是好消息不是坏消息**：v0.7 里那个「甲是一次性投资、废弃损失不大」的判断，现在直接兑现为「一分钱没花就避开了」。目前只损失了 v0.1 那点 Hermes 脚手架（约 400 行 Python + 一个 manifest）。

所有形态**共用同一份 core、同一份前端源码**，差异只在 adapter 与打包产物。完整宿主矩阵见 **§10.4**。

> 独立形态（`gsdbord serve`）**从 M1 就要跑起来**。理由比 v0.7 更强了：OpenClaw 的 UI 就是 sandboxed frame 加载一个 URL，**独立形态不再是「顺手做的副产品」，而是 OpenClaw 插件本身的前端来源**（§10.5）。

### 1.3 上游依赖与设计参考

**上游（唯一的真依赖）**：

- **[gsd-core](https://github.com/open-gsd/gsd-core)** —— **MIT / TypeScript**。GSDbord 的流程内核与状态真相来源。集成方式见 §9.8。
  - 协议 MIT ⇒ **代码可自由取用**，义务仅为保留版权声明（§9.7）。
  - **v0.6 起改为 vendor 内化**（复制入 `vendor/gsd-core/`），不是外部安装依赖。
    > ⚠️ 此处原写「不 fork、不 vendor 其内部实现，写操作走其 CLI」——那是 v0.5 的口径，**v0.6 已推翻**（§9.8），本行 v0.8 才补正。仍然成立的部分是：**尽量不改 vendored 文件本体**，改动集中在薄适配层，便于日后同步上游。

**设计参考**（借鉴模型与交互，不引入为依赖；技术栈选型调研见 §9.3）：

- **TAPD** —— 补 GSD 空缺的部分：需求分级、缺陷跟踪、时间盒迭代、优先级排序。**注意主从关系：GSD 模型为主，TAPD 概念只用于填空**（§3.5）。
- **Linear** —— 极简敏捷的操作手感：键盘优先、Cycle 自动滚动、无冗余字段。**交互体验主参考**。
- **Plane** —— 开源 Jira 替代中采用最广，其 Projects / Cycles / Modules / Issues 模型值得直接借鉴。同时是**最直接的竞品**（已有 AI 能力与原生 MCP server）。
- **Kanboard** —— 极轻量 PHP 看板，其「自动化动作（automatic actions）+ 插件系统 + WIP 限制」的设计最贴近 GSDbord 的规划。
- **GitHub Projects** —— 自定义字段 + 多视图（表格 / 看板 / 路线图）的轻量模型。

### 1.4 AI 工作流对标（仅思路参考，**不引入为依赖**）

| 项目 | 借鉴什么 | 明确不做什么 |
|------|---------|-------------|
| **n8n** | 「触发器 → 条件 → 动作」三段式规则模型（用于 §8.2 的 YAML 自动化） | 不集成 n8n；不做可视化节点画布 |
| **Dify** | 提示词编排与变量注入的组织方式 | 不集成 Dify；不做 LLM 网关 |

> 说明：GSDbord **不自带模型调用层**。插件形态下复用宿主（OpenClaw）的 agent 运行时与 CLI backend 生态（§8.4.2）；独立形态下需要自带一层最小适配。两者都走 `AgentRunner` 接口（§9.5-9）。
>
> ⚠️ **v0.8 区分两种「AI 执行」，别混**：
> - **AI 辅助管理**（§8.1–§8.3：澄清、拆解、排序、播报）—— 短请求，一次问答，用宿主 agent 或最小 LLM 调用即可
> - **AI 执行开发**（§8.4：驱动 Claude CLI 写代码）—— 长会话、多轮、要文件工具与 Git，**必须走专业开发 CLI，不是普通 LLM 调用**
>
> 这两者的运行时要求差一个量级。`AgentRunner` 主要为后者设计。

### 1.5 明确不做

写在这里是为了防止范围膨胀，后续要做需要重新决策：

- ❌ 可视化工作流编排画布
- ❌ 甘特图、资源工时管理、成本核算
- ❌ 与 TAPD 功能一对一对齐
- ❌ 引入 Redis / 消息队列 / Elasticsearch 等重型依赖（见 §9.2 依赖红线）

**v0.8 新增四条「不自己造」**（对应「充分利用 OpenClaw 生态」）：

- ❌ **不自己写 agent 运行时 / LLM 调用循环** —— 用 Claude CLI 等现成开发 agent（§8.4.1）
- ❌ **不自己写会话管理器**（PTY、流式解析、resume）—— 用 OpenClaw 的 CLI backend（§8.4.2）
- ❌ **不自己存会话 transcript 副本** —— 宿主已存两份，只存 `host_session_id` 指针（§8.4.4）
- ❌ **不自己写定时器** —— 用 OpenClaw 的 cron（§8.5）

> 这四条是有代价的：**换来的是对 OpenClaw 上游变更的依赖**（§15 已列）。对策是 `AgentRunner` 接口隔离 + 保留自己 spawn 的退路，而不是一开始就自己造。

**v0.4 从「不做」降级为「暂缓但预留」**（因终局是独立软件，不能彻底堵死）：

- ⏸ 企业级权限矩阵 —— M1 先建最小 `users` 表与 `actor` 字段，权限逻辑本身暂不做（§12.5）
- ⏸ 多租户服务端 —— 不做多租户，但**不假设单用户**；SQL 保持 Postgres 可移植（§9.5）
- ⏸ 自建账号体系 —— 抽 `AuthProvider` 接口；插件模式信任宿主身份，独立模式先用本地账号

## 3. 需求生命周期 + GSD 循环（主线流程）

**两段是串联的，不是二选一**：需求侧（GSDbord 补的漏斗）负责「做什么、按什么顺序」，GSD 循环（gsd-core 已有）负责「怎么做完」。

```
┌──── 需求漏斗（GSDbord 补，gsd-core 没有）────┐   ┌──── GSD 循环（gsd-core 已有）────┐
│ ① 收集 → ② 分析分类 → ③ 优先级排序           │ → │ Discuss →(UI Design)→ Plan →     │
│    ↑                                        │   │ Execute → Verify → Ship          │
└────┼───────────────────────────────────────┘   └──────┬─────────────────────┬─────┘
     │                                                  │  修复回环            │
     └────────── 缺陷 / 反馈回流 ───────────────────────┴─────────────────────┘
                                                    落地为 .planning/ 产物
```

衔接点：需求排序完成后进入 `ROADMAP.md` 成为一个 GSD **Phase**，由此启动 Discuss。详见 §3.5。

### ① 需求收集（Inbox）

| 能力 | 说明 | 阶段 |
|------|------|------|
| 快速捕获 | CLI / Dashboard / agent tool 一句话建需求，落到 `inbox` 状态 | M2 |
| 多来源接入 | 从对话记录、MD 文件、Git issue 导入 | M3 |
| **AI 去重** | 新需求入池时向量/关键词比对，提示「疑似重复 #xxx」 | M4 |
| 原始诉求留痕 | MD 正文保留提出人原话，不被后续加工覆盖 | M2 |

### ② 需求分析与分类

| 能力 | 说明 | 阶段 |
|------|------|------|
| 分类维度 | `type`（特性/优化/技术债/调研）、`module`、`labels` | M2 |
| **AI 澄清** | agent 读需求，提问缺失信息，补全背景 / 目标用户 / 约束 | M3 |
| **AI 生成验收标准** | 输出 Given-When-Then 形式的 AC，写入 MD 正文 | M3 |
| **AI 拆解** | 需求 → 子任务（前端/后端/测试），带估算建议 | M3 |
| 规模估算 | 故事点（斐波那契）或人日 | M2 |

### ③ 优先级排序

| 能力 | 说明 | 阶段 |
|------|------|------|
| 基础优先级 | `urgent / high / normal / low` | M0（已有） |
| **RICE 打分** | Reach × Impact × Confidence ÷ Effort，字段化存储、自动排序 | M2 |
| MoSCoW | Must / Should / Could / Won't，用于迭代范围裁剪 | M3 |
| **AI 排序建议** | 结合价值、依赖、风险给出排序建议 + 理由，**人确认后生效** | M4 |
| 依赖感知 | 被阻塞项自动降权并高亮 | M3 |

> 原则：AI **只给建议不自动改**优先级。优先级是产品判断，必须留人的决策点。

### ④ 实现与验证

| 能力 | 说明 | 阶段 |
|------|------|------|
| 迭代规划 | 需求拉入迭代，容量校验（§7） | M3 |
| 看板执行 | 拖拽流转 + WIP 限制 | M0（拖拽已有）/ M3（WIP） |
| 缺陷跟踪 | Bug 作为独立工作项，关联需求 / 迭代 | M2 |
| 验收 | 勾选 AC 清单，全绿方可进 `done`（准出条件，§4.3） | M3 |
| **AI 日报 / 周报** | 读 events 流水生成进展摘要与风险提示 | M4 |
| 度量 | 燃尽、CFD、周期时间、缺陷逃逸率（§11） | M4 |

### 3.5 GSD 阶段循环（核心逻辑，来自 gsd-core）

**这是 GSDbord 的骨架。** 以下为 gsd-core 既定模型，GSDbord **不改造、只呈现与聚合**。

| 阶段 | 做什么 | 产出产物 | 触发条件 |
|------|--------|---------|---------|
| **Discuss** | 在规划前先固化实现决策 | `XX-CONTEXT.md` | `ROADMAP.md` 中存在该 phase 的目标 |
| **UI Design**（条件） | 仅含视觉部分的 phase 才走 | `XX-UI-SPEC.md` | 视觉复杂度值得单独契约时 |
| **Plan** | 研究、拆解、校验计划能塞进新上下文 | `XX-RESEARCH.md`、`XX-YY-PLAN.md` | Discuss 完成；串行子 agent：researcher → planner → plan-checker |
| **Execute** | 按 wave 并行执行，每 executor 全新上下文 | 原子代码提交、`XX-YY-SUMMARY.md` | 计划校验通过 |
| **Verify** | 核对「建出来的」是否等于「想要的」 | `XX-VERIFICATION.md`、`XX-UAT.md` | 所有 executor 完成 |
| **Ship** | 建 PR、归档 phase 产物 | 更新 `STATE.md`、归档 | Verify 确认与需求一致 |

**层级与并行模型**：

```
Project
└── Phase（十进制编号 01, 02…；一个可交付单元，跑完整循环）
    └── Plan（XX-YY）
        └── Wave（按依赖分组，同 wave 内并行）

Plan 01（无依赖）  ─┐
Plan 02（无依赖）  ─┼── Wave 1（并行）
Plan 03（依赖 01） ─┴── Wave 2（等待）
```

每个 executor 拿到全新的 200K 上下文窗口（大模型可至 1M），这是 gsd-core 对抗 context rot 的核心手段。

**回环**：Verify 可产出定向修复计划，即存在 Verify → Execute 的回退。GSDbord 必须把这个回环**显式画出来**并计入度量（§11 的「Verify 返工率」）。

**GSD 概念与 GSDbord 既有设计的对应关系**：

| GSD 概念 | GSDbord 对应 | 说明 |
|---------|-------------|------|
| `PROJECT.md` | Product（§5.1） | 愿景、约束、决策 |
| `REQUIREMENTS.md`（v1/v2/out-of-scope） | 需求分级（§3.3 的 MoSCoW） | GSD 只有平铺文档，GSDbord 补排序与打分 |
| `ROADMAP.md`（phase 分解 + 状态） | 工作规划 / 路线图（§6） | 天然对应，直接渲染 |
| **Phase** | 介于 Release 与 Iteration 之间 | **依赖驱动，非时间盒**；时间盒迭代是 GSDbord 的补充概念 |
| **Plan（XX-YY）** | WorkItem `type=task`（§5.2） | |
| **Wave** | 并行执行分组 | GSDbord 新增可视化维度 |
| `STATE.md`（position / decisions / blockers / metrics） | 当前位置 + 阻塞 + events 源 | **度量的原始输入** |
| `continue-here.md` | 会话恢复上下文 | 来自 `/gsd-pause-work` |

**GSD 没有、由 GSDbord 补的**：assignee / 多人视图、缺陷实体、时间盒迭代与容量、RICE 优先级、跨项目聚合、度量历史与图表。

## 4. 模块① 流程管理

**目标：让「研发流程标准化」可配置、可执行、可审计**，而不是写在 wiki 里没人遵守。

### 4.1 工作流定义

**内建默认工作流就是 GSD 阶段循环**（§3.5），不是通用 kanban 套壳。这是 GSDbord 与其他看板的根本区别。

```
phase（GSD 主流程，来自 gsd-core，GSDbord 不改造）：
  discuss →[ui_design]→ plan → execute → verify → ship
                                            └── 修复回环 ──┘（Verify → Execute）

story（需求漏斗，GSDbord 补）：
  inbox → analyzing → ready → （进入 ROADMAP.md 成为 phase）
              └── rejected / deferred ──┘

task（= GSD 的 Plan，XX-YY）：
  todo → doing → blocked → done

bug（GSD 无此实体，GSDbord 补）：
  new → confirmed → fixing → fixed → verifying → closed
            └─ rejected / duplicate ─┘
```

要点：

- `phase` 的状态**不由 GSDbord 定义**，而是读 `.planning/ROADMAP.md` 与 `STATE.md` 得到；GSDbord 只呈现与聚合（§12.1）。
- 因此 `phase` 的流转**不走 GSDbord 的准入准出检查器**（§4.3），gate 由 gsd-core 自己把（plan-checker、verifier）。GSDbord 的检查器只作用于 `story` / `task` / `bug`。
- v0.1 的五列（`triage/todo/doing/blocked/done`）保留为 `task` 的默认流；`inbox` 取代 `triage` 作为 story 入口。

配置示例（`<GSDBORD_HOME>/workflows.yaml`；独立形态为 `~/.gsdbord/`，插件形态由 adapter 注入宿主目录）：

```yaml
story:
  states:
    - { id: inbox,     label: 需求池,   category: todo }
    - { id: analyzing, label: 分析中,   category: todo }
    - { id: ready,     label: 待排期,   category: todo,  entry: [has_ac, has_estimate] }
    - { id: doing,     label: 开发中,   category: active, wip: 3 }
    - { id: verifying, label: 验证中,   category: active }
    - { id: done,      label: 已完成,   category: done,  entry: [all_ac_checked] }
  transitions:
    - { from: inbox, to: analyzing }
    - { from: "*",   to: rejected, requires_comment: true }
```

### 4.2 流程要素

| 要素 | 说明 | 阶段 |
|------|------|------|
| 状态与流转 | 允许的迁移路径，非法流转被拒 | M3 |
| **准入/准出条件** | 如「进 done 必须 AC 全绿」「进 ready 必须有估算」 | M3 |
| WIP 限制 | 每状态在制品上限，超限告警 | M3 |
| 必填字段规则 | 按状态要求字段（如进 fixing 必须有负责人） | M4 |
| 流转留痕 | 每次迁移写 `events`（from/to/actor/时间） | **M2（度量依赖，优先）** |
| 工作流模板 | 内置 `scrum` / `kanban` / `bugfix` 三套预设，一键套用 | M3 |
| 自定义字段 | 按产品定义扩展字段，存 `extra_json` | M4 |

### 4.3 准入/准出条件（内置检查器）

| 检查器 | 语义 |
|--------|------|
| `has_ac` | 已有验收标准 |
| `all_ac_checked` | 验收标准全部勾选 |
| `has_estimate` | 已估算 |
| `has_assignee` | 已指派 |
| `no_open_blockers` | 无未解除的 `blocks` 关联 |
| `has_comment` | 本次流转填写了说明 |

> 检查器**默认全部关闭**，团队按需开启。流程管理最大的失败模式是一上来就卡死所有人。

## 5. 模块② 工作项管理

### 5.1 层级

```
Workspace（工作区，= 一个 GSDbord 实例）
└── Product（产品/项目）
    ├── Release（发布计划）→ Iteration（迭代）→ WorkItem
    └── WorkItem（不属于任何迭代 → 需求池）
```

### 5.2 WorkItem 统一模型

**决策：单表 + `type` 字段**，不为 story / task / bug 分表。理由：插件量级下分表带来的查询与 UI 复杂度大于收益；差异字段进 `extra_json`。

| type | 含义 | 典型父子关系 |
|------|------|-------------|
| `epic` | 史诗 / 大需求 | 父：Release |
| `story` | 需求 / 用户故事 | 父：epic；子：task |
| `task` | 任务 | 父：story |
| `bug` | 缺陷 | 关联：story / iteration |
| `spike` | 技术调研 | 独立 |

### 5.3 关联关系

`links` 表，`(from_id, to_id, kind)`：

| kind | 语义 |
|------|------|
| `parent` | 层级归属 |
| `blocks` | 阻塞（影响优先级与预警） |
| `relates` | 一般关联 |
| `duplicates` | 重复 |
| `verifies` | bug 验证某 story |

### 5.4 操作与视图

| 能力 | 说明 | 阶段 |
|------|------|------|
| 看板视图 | 按状态分列，拖拽流转 | M0 ✅ |
| **表格视图** | 批量查看/编辑，列可配 | M3 |
| 列表视图 | 分组（按迭代/负责人/优先级） | M3 |
| 筛选器 | 组合条件，可保存为「我的视图」 | M3 |
| 批量操作 | 多选后批量改状态/负责人/迭代 | M3 |
| 详情抽屉 | 字段 + MD 正文 + AC + 评论 + 变更历史 | M0 部分 ✅ / M2 补全 |
| 全文检索 | 标题 + MD 正文（SQLite FTS5） | M3 |
| 变更历史 | 从 `events` 渲染时间线 | M2 |

## 8. AI 工作流层 + 执行调度（横切）

这是 GSDbord 相对 TAPD 的**核心差异化**，必须做实。

> §8.1–§8.3 是「AI 辅助管理」（澄清、拆解、排序、播报）；**§8.4–§8.6 是「AI 执行开发」的调度**（v0.8 新增，模块⑥）。两者性质不同：前者是产品功能，后者是产品骨架。

### 8.1 Agent Tools（**以 MCP 为主契约**）

**v0.5 决策：工具层实现为一个 MCP server，不为每个宿主写一套。**

理由：宿主会越来越多（Hermes / OpenClaw / Codex / VS Code / Cursor…），逐个写 agent tool 适配是 O(n) 成本；MCP 是当前 agent 生态的通用契约，一次实现即可全覆盖。宿主若有自己的原生工具注册机制，adapter 写一层**薄桥接**转发到同一批 handler 即可，业务逻辑仍在 `gsdbord/tools.py`。

> 参照：Plane 已提供原生 MCP server（§9.3），这是它当前领先的地方之一。

工具集：

| 工具 | 用途 |
|------|------|
| `gsdbord_search` | 按条件检索工作项（状态/负责人/迭代/标签/全文） |
| `gsdbord_get` | 读单个工作项（含 MD 正文与 AC） |
| `gsdbord_create` | 建工作项 |
| `gsdbord_update` | 改字段 / 移状态（走流程校验） |
| `gsdbord_link` | 建立关联 |
| `gsdbord_comment` | 追加评论到 MD |
| `gsdbord_plan_iteration` | 迭代规划：给候选集与容量，返回建议范围 |
| `gsdbord_report` | 生成日报 / 周报 / 迭代总结 |
| `gsdbord_metrics` | 取度量数据 |

> 写操作工具需带 `dry_run` 参数，agent 默认先预演再执行。

### 8.2 自动化规则

轻量三段式（**触发器 → 条件 → 动作**），YAML 配置于 `<GSDBORD_HOME>/automations.yaml`。规则模型参考 n8n，**但不引入 n8n，也不做画布**（§1.4）：

```yaml
- name: 阻塞超时预警
  on: item.status_changed
  if: status == 'blocked' && duration_in_status > '2d'
  then:
    - notify: { channel: dashboard, level: warn }
    - ai_task: "分析 {{item.id}} 阻塞原因，给出 2 条解法建议，写入评论"

- name: 需求入池自动分析
  on: item.created
  if: type == 'story' && status == 'inbox'
  then:
    - ai_task: "澄清需求 {{item.id}}，补全验收标准，检测是否与既有需求重复"
    - set: { status: analyzing }
```

内建动作：`set` / `notify` / `link` / `comment` / `ai_task`（把提示词丢给宿主 agent 执行）。

### 8.3 AI 辅助环节汇总

| 环节 | 输入 | 输出 | 是否需人确认 |
|------|------|------|-------------|
| 需求澄清 | 原始诉求 | 追问 + 补全后的描述 | 是 |
| 验收标准生成 | 需求描述 | Given-When-Then 清单 | 是 |
| 需求拆解 | story | 子 task 列表 + 估算 | 是 |
| 重复检测 | 新 story | 疑似重复列表 | 是 |
| 优先级建议 | 需求池 | RICE 打分 + 排序理由 | **是（强制）** |
| Release 划分建议 | 目标 + 需求池 | Release 草案 + 风险 | 是 |
| 迭代规划 | 候选集 + 历史速率 | 建议范围 + 风险 | 是 |
| 进展播报 | events 流水 | 日报 / 周报 | 否 |
| 风险预警 | 状态停留时长 | 预警项 | 否 |

### 8.4 执行调度层（v0.8 新增，模块⑥ 核心）

**一句话定位：**

> **GSDbord 是调度层，不是开发执行者。真实执行者是 Claude CLI / codex / opencode 等专业开发 agent。**
> 目标不是让 AI 自主完成所有开发，而是把开发执行变成**可排队、可观察、可验证、可接管**的异步流程。

#### 8.4.1 职责红线

| GSDbord 做 | GSDbord 不做 |
|-----------|-------------|
| 决定**哪个工作项该开工**（按 GSD 阶段 + 依赖 + WIP） | ❌ 自己写代码、自己改文件 |
| 组装会话的**上下文包**（workspace、phase、要读的产物、skills、MCP） | ❌ 自带 LLM 调用层、自己跑 agent loop |
| 启动 / 排队 / 观察 / 中止会话 | ❌ 替用户做架构决策与验收判断 |
| **落账**：会话 ↔ 工作项 ↔ GSD phase 的三元映射 + 全过程留档 | ❌ 复制一份会话历史（宿主已有，§8.4.4） |
| 把「需要人」的时刻**推到人面前** | ❌ 卡住了自己硬猜着继续 |

**人保留的四个决策点**（不可让渡，任何自动化都不越过）：

```
规划 ──→ 关键决策 ──→ 〔agent 执行〕──→ 验收 ──→ 返工判断
 人          人           机器            人         人
```

对应到 GSD 循环（§3.5）：

| GSD 阶段 | 谁主导 | GSDbord 的角色 |
|---------|-------|--------------|
| Discuss | **人**（agent 辅助提问） | 提供上下文、记录决策入 `XX-CONTEXT.md` |
| Plan | 机器起草 → **人过目** | 起会话；`plan-checker` 未过则不放行 Execute |
| **Execute** | **机器**（可无人值守） | ★ 主战场：按 wave 排队、并行度控制、实时观察 |
| Verify | 机器跑 → **人验收** | 把 `XX-VERIFICATION.md` / `XX-UAT.md` 推成待办卡 |
| Ship | **人** | 归档、更新 `STATE.md`、度量落账 |

⇒ **只有 Execute 是可以放手的**。其余四个阶段 GSDbord 只做「把材料准备好、把人叫来」。

#### 8.4.2 ⚠️ 关键发现：OpenClaw 已内建 CLI backend，执行层大半可复用

**（2026-07 查官方文档，本机未装 OpenClaw，未实测）**

这是 v0.8 调研中最有价值的一条，直接回应「充分利用 OpenClaw 生态，不要啥都自己开发」：

**OpenClaw 有一整套把外部 CLI 包成会话后端的机制**，并已捆绑 `claude-cli`：

| 能力 | OpenClaw 已提供 | 出处 |
|------|----------------|------|
| 注册 CLI 后端 | `api.registerCliBackend(...)`，插件级 API，有专门文档 | `plugins/cli-backend-plugins` |
| Claude Code 后端 | 捆绑 `claude-cli`，默认参数 `-p --output-format stream-json --include-partial-messages --verbose` | `gateway/cli-backends` |
| **流式解析** | `output: "jsonl"` + `jsonlDialect: "claude-stream-json"` —— 解析 assistant 消息、tool 事件、session id | 同上 |
| **会话持久化 + resume** | `sessionArgs: ["--session-id","{sessionId}"]`、`sessionMode: "always"`；session id 跨 OpenClaw 重启存活；resume 前**校验 project transcripts** | 同上 |
| 进程复用 | 「keeps Claude's stdio process alive per session during active use，then resumes from the stored ID on subsequent turns」 | 同上 |
| **MCP 桥** | `bundleMcp: true` ⇒ 「spawns a loopback HTTP MCP server that exposes gateway tools to the CLI process」，带 per-run 授权 `OPENCLAW_MCP_TOKEN` | 同上 |
| **skills 透传** | 「Skills with materialized paths pass through via `--plugin-dir` as a temporary Claude Code plugin」 | 同上 |
| 上下文压缩归属 | `ownsNativeCompaction: true`（Claude Code 自己 compact，OpenClaw 的 summarizer 不介入） | 同上 |
| 会话历史存储 | `~/.openclaw/agents/<agentId>/agent/openclaw-agent.sqlite` + 归档 transcripts 于 `sessions/` | `concepts/session` |
| 多 agent 编排 | `sessions_spawn`（非阻塞，返回 `runId` + `childSessionKey`）/ `sessions_yield` / subagents 树视图 | `concepts/session-tool` |

**⇒ 结论：GSDbord 不该自己写会话管理器。** PTY、流式解析、session resume、MCP 注入、skills 挂载、历史落库——这些全是已解决问题。GSDbord 该做的是**上面那一层：账本 + 排队 + GSD 状态机 + 人机交接点**。

**你的两条指示在这里冲突了，必须拍板**（→ §19 决策 B）：

> 「多用**交互模式**，少用 `claude -p` 一次性模式」 vs 「**充分利用 OpenClaw 生态**」
> —— OpenClaw 的 `claude-cli` 后端用的**正是 `-p`**。

先把事实摆清楚，因为「`-p` 就是一次性」这个判断**不完全准确**：

| | Claude Agent SDK 官方口径 | 对应做法 | 多轮上下文 | 中途插话 / 排队 | **实时打断** | **权限请求上抛** |
|---|---|---|---|---|---|---|
| **Streaming Input Mode**（官方推荐） | 「a long lived process that takes in user input, handles interruptions, surfaces permission requests, and handles session management」 | Agent SDK 长驻会话 | ✅ 天然 | ✅ | ✅ | ✅ |
| **Single Message Input** | 「One-shot queries that **use session state and resuming**」 | `-p` + `--session-id` + resume ← **OpenClaw 用这个** | ✅ 靠 resume | ❌ | ❌ | ❌ |
| 裸 `claude -p "..."` | —— | 无 session | ❌ | ❌ | ❌ | ❌ |

官方明确列出 Single Message 模式**不支持**的四项（原文）：

> 「Direct image attachments in messages / Dynamic message queueing / Real-time interruption / Natural multi-turn conversations」

**所以准确的说法是**：`-p` 是**传输模式**，不是会话模式。加上 `--session-id` + resume 之后上下文是连续的，你担心的「每次从零开始」不会发生。真正丢掉的是**实时打断**和**权限请求上抛**这两项——而这两项恰好命中「可接管」。

**建议方案（分层，同时满足两条指示）**：

```
默认路径：OpenClaw claude-cli 后端（-p + session-id + resume）
          ├─ 白拿 MCP 桥、skills 透传、历史落库、native compaction
          └─ 代价：不能实时打断，权限须预设 permission-mode
                    ↓ 人要介入时
接管路径：人在真终端跑  claude --resume <session-id>
          └─ 会话 id 就在 GSDbord 的账本里，几乎零成本 ★
                    ↓ 只有需要「跑着的时候插话」时才上
增强路径：Agent SDK 长驻会话（自建，M4+）
          └─ 仅对少数需要边跑边引导的场景开
```

> ★ **接管路径是这套设计里性价比最高的一环**：`-p --session-id` 写入的是 Claude Code 自己的 project transcript（OpenClaw 文档提到 resume 前会「verified against project transcripts」），因此人可以直接 `claude --resume <id>` 在真终端里以**完整交互模式**接手同一个会话。**待实测（§10.3-13）**，但证据链是通的。
> 这比「在 Web UI 里做一个假终端」强得多，也符合「Dashboard 是复杂问题处理**入口**」而非处理现场。

#### 8.4.3 会话生命周期与看板的关系

```
work_item (status=ready)
    │  ← 人点「开工」，或自动化规则触发（§8.2），或每日巡检建议（§8.5）
    ▼
run（一次会话）  status: queued → running → awaiting_human → done / failed / aborted
    │
    ├─ 组装上下文包：workspace 路径 + GSD phase + 要读的 .planning/ 产物
    │                + 该项目的 skills + 该项目的 MCP（§8.4.5）
    ├─ 提交给 OpenClaw claude-cli 后端，拿回 session_id
    ├─ 流式事件 → 写 run_events → WebSocket 推到看板卡片上
    │
    ├─ 命中「需要人」→ awaiting_human，卡片进「待我处理」列 + 推送通知
    └─ 结束 → 写 run 结果、更新 work_item、落归档（§8.6）
```

**`awaiting_human` 是这套设计的枢纽状态**，触发条件：

| 触发 | 例子 |
|------|------|
| agent 显式提问 | 「两种实现方式，选哪个」 |
| 权限被拒 / 需要审批 | 要改 CI 配置、要装依赖 |
| Verify 失败 | `XX-VERIFICATION.md` 判定不符，等人决定返工范围 |
| 超时 / 无进展 | 单会话超 N 分钟无 tool 事件 |
| 预算超限 | token / 时长超阈值 |
| plan-checker 未通过 | 计划质量不过关，不放行 Execute |

> **红线：`awaiting_human` 永不自动跨过。** 宁可停在那儿等一天，也不猜着往下做——这是「用户保留关键决策」的落地方式。

**并行度控制**：GSD 的 wave 模型（§3.5）天然给出并行边界；同 wave 内的 plan 可并发起会话。GSDbord 需要一个全局 `max_concurrent_runs`（默认建议 2–3），因为并发会话抢的是同一台机器的 CPU、同一个 API 配额，也抢**同一个 Git 工作区**。

> ⚠️ **同一 repo 并发写会互相踩**。GSD 的 wave 假设了并行 executor，但那是靠 fresh context 隔离**上下文**，没隔离**文件系统**。GSDbord 必须做出选择（→ §19 决策 C）：
> - **C1 串行化同 repo**：简单可靠，牺牲并行度
> - **C2 git worktree 隔离**：每个 run 一个 worktree，跑完合并。成本中等，收益是真并行
> - **C3 信任 wave 划分**：假定同 wave 的 plan 不碰同一批文件（gsd-core 的 planner 本就按依赖分组）
>
> 倾向 **C1 起步 + C2 作为 M3 增强**。C3 太依赖 planner 的正确性，一次冲突就毁掉一整轮执行的可信度。

#### 8.4.4 数据落点：不复制宿主已有的东西

| 数据 | 存哪 | 理由 |
|------|------|------|
| 会话原始 transcript | **OpenClaw**（`~/.openclaw/agents/<id>/…sqlite` + `sessions/`）与 **Claude Code**（project transcripts） | 已经有两份了，再存第三份是纯负债 |
| `runs` 表：run_id ↔ session_id ↔ work_item ↔ phase ↔ 起止时间 ↔ 结果 ↔ 成本 | **GSDbord SQLite** | 宿主不知道「工作项」这个概念，这是 GSDbord 独有实体（§12.1） |
| `run_events`：里程碑事件（阶段切换、tool 使用摘要、awaiting_human 原因、错误） | **GSDbord SQLite** | 度量（§11）与看板实时展示需要；**只存摘要不存全文** |
| 会话产出的 GSD 产物 | **文件**（`.planning/`） | 铁律不变（§12.1） |
| 复盘档 | **文件**（§8.6） | 要能 Git 版本化、要能被 agent 读 |

> **「全过程需保存」= 保存指针 + 摘要 + 产物，不是保存全文副本。** 全文在宿主那儿，GSDbord 存 `session_id` 就能随时调出（也能 `claude --resume` 直接进去）。真正需要自己存的是**跨会话、跨项目才能算出来的东西**：谁在什么时候因为什么卡住了、返工了几次、花了多少。

#### 8.4.5 skills 与 MCP 的透传

需求：「Claude CLI 开发时要能调用项目该用的 skills 和 MCP」。

OpenClaw 侧已提供机制，但有两个坑必须实测：

| 项 | 机制 | ⚠️ 坑 |
|----|------|------|
| **skills** | `--plugin-dir` 挂成临时 Claude Code plugin | 是 OpenClaw 自己的 skills（clawhub.ai / 本地插件目录）。**项目 `.claude/skills/` 是否照常加载，待实测** |
| **MCP** | `bundleMcp: true` → loopback HTTP MCP server 暴露 **gateway tools** | 暴露的是**网关工具**，不是项目 `.mcp.json` 里的 MCP。**两者能否并存，待实测** |
| **原生工具** | `nativeToolMode: "always-on" \| "selectable" \| "disabled"` | ⚠️ 文档说 restricted run 下「Claude's native tools are disabled」。**开发场景必须 `always-on`**——没有 Read/Edit/Bash 就不用谈写代码了 |

> 若实测发现 OpenClaw 的 bundleMcp 会挤掉项目自己的 MCP 配置，退路是**不走 OpenClaw 的 MCP 桥**：`bundleMcp: false`，让 GSDbord 直接把项目该用的 MCP 写进会话的 `--mcp-config`，把 GSDbord 自己的工具也作为一个 MCP server 暴露（§8.1 本来就要做 MCP server，正好复用）。
> 这条退路值得优先验证，因为它同时更符合「项目该用什么就用什么」的语义。

### 8.5 每日巡检（辅助通道）

**定位：辅助通道，不替代交互开发主流程，也不自动替用户做复杂决策。**

| 项 | 设定 |
|----|------|
| 触发 | OpenClaw 的 cron（生态已有，不自建定时器）；每个项目可独立开关 |
| 适用范围 | **只对标记为「需值守」的项目开** —— 不是所有项目都要巡检 |
| 产出 | 一张**巡检报告卡** + 一批**建议卡**，进「待我处理」列 |
| 权限 | **默认只读 + 只建议**。写操作与执行一律等人点 |

巡检检查项：

| 检查 | 输出 |
|------|------|
| `.planning/` 与看板索引是否一致 | 不一致 → 建议 `gsdbord reindex` |
| 有无 `awaiting_human` 挂了超过 N 小时 | 汇总提醒（这是最有价值的一项） |
| 有无 phase 停在某阶段超阈值 | 阻塞预警（§11 阶段停留分布） |
| 有无 Verify 失败未处理 | 返工待决 |
| 有无 plan 已通过校验但没排上 Execute | 建议开工（**建议，不自动开**） |
| 上一日 run 的失败与成本汇总 | 日报（§8.3 进展播报） |

**升级路径**（可选，默认关）：某类低风险项可配置为「巡检直接开工」，例如 `type=chore` 且有现成 plan 且 wave 内无依赖。**默认全关**，与 §4.3 检查器同一原则。

> 巡检的失败模式是**变成噪音**。对策：报告卡合并成一张、无事发生时不建卡、同一问题不重复提醒（记 `last_notified_at`）。

### 8.6 复盘与归档

「全过程需保存，便于复盘」的具体落法：

```
<项目仓库>/.planning/phases/XX-phase-name/
└── runs/                          ← GSDbord 新增，但放在 GSD 布局内
    └── <run_id>/
        ├── META.json              # session_id / 起止 / 模型 / 成本 / 结果
        ├── TIMELINE.md            # 里程碑时间线（人可读）
        └── HANDOFF.md             # awaiting_human 的问答记录与人的决定 ★
```

> ⚠️ 这里与 §12.1 铁律「不往 `.planning/` 写自有字段」有张力。**分辨方式：不改上游既有文件的格式，只在 phase 目录下加一个上游没有的 `runs/` 子目录。** 上游 gsd-core 不认识它，但也不会被它破坏；用户 Git 里能看到、能 diff、能跟着 phase 一起归档。
> 若后续发现 gsd-core 的归档逻辑会清理未知目录，退路是移到 `<GSDBORD_HOME>/runs/<project>/<phase>/`，代价是失去「跟着代码一起版本化」。**待实测（§10.3-14）。**

**`HANDOFF.md` 是复盘里最值钱的文件**——它记录的是「机器在哪儿卡住、人怎么决定的」。这正是 §11「Verify 返工率」「人机操作比」两个指标的原始素材，也是将来沉淀成 skills / CONTEXT 模板的来源。

复盘视图（M4）：

| 视图 | 回答 |
|------|------|
| Run 时间线 | 这个 phase 一共跑了几次会话、每次多久、卡在哪 |
| 返工链 | Verify → Execute 的回环，每次返工的原因 |
| 人工介入点汇总 | 人一共被叫了几次、为什么、平均等了多久 |
| 成本 | 每 phase / 每 work_item 的 token 与时长 |

## 9. 技术栈决策

### 9.1 后端语言：⚠️ **v0.8 决策重开——建议转 TypeScript**（→ §19 决策 A）

**旧结论（v0.1–v0.7）：Python，因为「Hermes 插件的后端入口就是 `plugin_api.py`，宿主强制」。**

**这个理由随 Hermes 退场一起消失了。** 原文写的是「只要还要做插件形态，后端必须是 Python」——现在唯一的插件形态是 OpenClaw，而 **OpenClaw 只支持 JS/TS**。整条论证链断了，结论必须重算。

#### 重算：七条论据，六条指向 TypeScript

| # | 论据 | 指向 |
|---|------|------|
| 1 | **唯一宿主 OpenClaw 只认 JS/TS** —— 插件入口是 `definePluginEntry`，`openclaw/plugin-sdk/*` subpath 导入。Python 只能当 sidecar 子进程 | **TS** |
| 2 | **分发是 npm 包** —— npm 包里塞 Python 依赖是分发地狱：用户得自己有 python3 + 正确版本 + 装依赖。TS 就是 `npm i` | **TS** |
| 3 | **`api.registerCliBackend` 是 TS API**（§8.4.2）—— 执行调度层要用 OpenClaw 的 CLI backend 生态，就得在 TS 里注册。Python 侧连不上这套 | **TS** |
| 4 | **gsd-core 本身是 TypeScript** —— 转 TS 后 `vendor/gsd-core/` 可**原生 import**，`gsd-tools.cjs` 直接 `require`，subprocess 层整个消失（§9.8 简化） | **TS** |
| 5 | **前端必须是 TS** —— Hermes SDK 白拿 React 的路没了，前端要自己写（§9.2）。同语言意味着 domain 类型定义**前后端共享一份**，不用维护两套 schema | **TS** |
| 6 | **将来 VS Code 扩展 in-process** —— §10.4 原本要为 VS Code 写 Python sidecar，转 TS 后这个成本归零 | **TS** |
| 7 | 现有 Python 代码资产 | Python，但**只有约 400 行**（`db.py` 318 + `config.py` 80 + `md_store`），且是最机械的 CRUD。重写是几小时的事，不是沉没成本 |

**唯一真正需要问你的是熟悉度**：你写 TS/Node 的手感如何？这是我不知道的变量，也是唯一可能推翻上面六条的因素。若 TS 生疏，代价是整个项目每一行都慢——那另一条路是**保 Python 走 sidecar**，但要认下这些账：

| Python + sidecar 的代价 | 严重度 |
|----------------------|-------|
| OpenClaw 插件仍必须有个 TS 壳（进程管理 + iframe + 路由代理） | 中——躲不掉，只是薄 |
| npm 包分发要求用户自备 Python 环境 | **高——这是采纳率杀手** |
| 用不上 `registerCliBackend`，执行调度层得自己写会话管理（PTY / stream-json 解析 / resume） | **高——白扔掉 §8.4.2 那一整表** |
| gsd-core 仍走 subprocess，跨语言传状态 | 中 |
| 前后端两套类型定义 | 中 |

> **我的建议：转 TypeScript，趁现在只有 400 行。** 这个决策每晚一周都更贵，而且它决定 §9.8（gsd-core 集成方式）、§8.4（能否复用 CLI backend）、§10.4（VS Code 成本）三处的写法。

#### 若采纳 TS，具体选型

| 项 | 选择 | 理由 |
|----|------|------|
| 语言 / 运行时 | **TypeScript + Node**（版本下限跟随 OpenClaw 要求，**待确认**） | 宿主决定 |
| HTTP 框架 | **Hono** 或 Fastify | 轻、TS 原生、能同时跑在独立 server 与插件路由里；`get_router()` 的对等物是一个可挂载的 app |
| 数据库 | **SQLite**，驱动 `better-sqlite3`（含 FTS5、同步 API）或 Node 内建 `node:sqlite` | 前者稳妥且 FTS5 确定可用；后者零依赖但要看 Node 版本下限 |
| ORM | **不用 ORM**，手写 SQL（结论不变） | 表少、查询简单 |
| 全文检索 | **SQLite FTS5**（结论不变，仍封在 `search.ts` 后，§9.5-7） | 内建 |
| 校验 | **Zod** | 前后端共享 schema，同时给出 TS 类型与运行时校验 |
| 配置 | YAML + JSON（结论不变） | |
| gsd-core | **原生 import**，不再 subprocess（§9.8 改写） | 同语言的最大红利 |
| 打包 | **tsup** 或 Vite（库模式） | 出 npm 包 + 独立 server 两个产物 |
| 第三方依赖 | **尽量少** —— native 模块尤其克制（`better-sqlite3` 需 prebuilt；若 OpenClaw 环境编译不过就退 `node:sqlite`） | in-process 跑在 Gateway 里，装不上就整个插件废掉 |

> **⚠️ 转语言不等于重开架构。** §9.5（十项预留）、§10.1（core / adapters / web 三分）、§12（数据设计）、§8.4（调度层设计）**全部原样成立**，只是文件后缀从 `.py` 变 `.ts`。要改写的只有 §9.1 本节、§9.8 的集成方式、§10.4 的 VS Code 行。

### 9.2 前端：⚠️ **v0.8 反转——Vite 从「可延后」变「M1 必做」**

**v0.6/v0.7 的「构建链可延后」建立在一个前提上：`window.__HERMES_PLUGIN_SDK__` 白送 React + shadcn，照抄官方 kanban 的无构建 IIFE 写法就能上线。Hermes 退场，这个前提没了。**

现在的实情：

| | v0.7（有 Hermes） | v0.8（只有 OpenClaw） |
|---|---|---|
| React 来源 | 宿主 SDK 白送 | **自己打包** |
| UI 原语 | 宿主给 shadcn 一套 | **自己装 / 自己写** |
| 产物形态 | IIFE 注入 | **HTML + JS + CSS（sandboxed frame 加载的完整页面）** |
| 构建链 | 可以没有 | **必须有** |

⇒ **`dist/standalone/`（原 §9.5-2 的「顺手副产品」）现在是唯一前端产物，也就是 OpenClaw 插件的前端本体。** 这同时简化了一件事：**不用再出双产物了**，IIFE 那一路取消。

选型（M1 落地）：

| 项 | 选择 | 理由 |
|----|------|------|
| 构建 | **Vite** → 静态站（HTML + hashed assets） | sandboxed frame 直接加载；独立形态同一份 |
| 框架 | **React + TypeScript** | 生态最厚；与后端同语言则 domain 类型共享（§9.1-5） |
| UI 原语 | **shadcn/ui**（复制式，非依赖）+ Tailwind | 自己持有代码，不受宿主主题摆布；体积可控 |
| 状态 | Zustand 或原生 Context | 不上 Redux |
| 拖拽 | **dnd-kit** | 轻、可访问性好、有触摸支持——这块原本想从 Hermes 白拿，现在得自己接 |
| 图表 | **轻量库或手写 SVG** | 只有燃尽/CFD/周期时间三种图，**不引 ECharts 全量** |
| 实时 | **WebSocket**（自己接） | 原本想白拿官方 kanban 的实现，现在自己写。执行调度层（§8.4）**强依赖**它——会话流式事件必须实时推 |
| 路由 | 轻量（`wouter` 或手写） | 单页多视图，不需要 React Router 全量 |

**这次反转的净代价**（诚实记账）：

| 丢掉的白拿项 | 自己实现的成本 |
|-------------|--------------|
| 拖拽 + 触摸 pointer 回退 | dnd-kit 接一下，**低** |
| WebSocket 实时刷新 | 需要，但执行调度层本来就要，**中** |
| shadcn 原语与宿主视觉一致 | 复制 shadcn，**低**；且不再受宿主主题约束（有得有失） |
| i18n 骨架 | **低**，本来只需中文 |
| 3917 行可参考的同构代码 | **这是真损失** —— 但它服务的是一个已经不做的宿主 |

> 结论：反转的代价是「中低」，而且换来了不必再为 Hermes 的 IIFE 形态做任何妥协。**前端从此只有一种形态。**

> **关键约束不变：产物必须自包含，不能有运行时 CDN 依赖。** OpenClaw 的 sandboxed frame 有 CSP，外链大概率被拦（§10.3-8 待实测）。

**依赖红线**（违反需重新决策）：不引 Postgres / Redis / 消息队列 / Elasticsearch。GSDbord 必须能在一台笔记本上零配置跑起来。

> ⚠️ v0.8 对「独立后台进程」这条红线开一个**例外**：执行调度层（§8.4）本质上要管理长驻子进程（会话）。这不违反红线的精神——它不是「为了跑 GSDbord 而必须常驻的基础设施」，而是**业务本体**。区别在于：没有它 GSDbord 就没有功能；而 Redis 只是为了让别的东西快一点。

v0.6 的推理仍然有效，只是结论换了归属：上表项目全是**独立应用**，跨架构抠组件是伪快路。而 v0.8 的新情况是——**GSDbord 自己也变成独立应用了**（Vite 静态站 + Hono 后端，§9.2）。

这意味着上表项目的**架构冲突消失了一半**：不再有 IIFE 注入的形态障碍，剩下的障碍只是它们各自的技术栈（Redux-Saga / Sails / PHP / Go）与重型依赖。

但结论仍然是不 fork，理由从「架构冲突」换成下面三条（见本节末）。**唯一变化是 Planka 从「只看效果」升级为「可读代码的候选」**——它是 MIT + React，形态上首次与 GSDbord 对齐。

v0.8 分工：

| 用途 | 抄谁 | 说明 |
|------|------|------|
| **看板 UI / 拖拽** | **自己写**（dnd-kit） | 无同构可抄源；成本低（§9.2 记账） |
| 看板交互与组件划分**参考** | **Planka**（MIT + React，可读代码） | 形态首次对齐；仍不整体取用（Redux-Saga 太重） |
| 流程引擎与自动化动作**设计** | Kanboard | **读设计，不抄代码**（PHP + jQuery） |
| 交互手感参考 | Linear | 看效果 |
| 数据模型参考 | Plane | **只读文档**（AGPL，§9.7） |
| **执行调度 / CLI 会话管理** | **不抄——用 OpenClaw 生态**（§8.4.2） | 这是 v0.8 最大的「不用自己写」 |

**结论：仍然不 fork 整个应用。** 理由（v0.8 重述，架构冲突不再是主因）：

1. **省错了地方** —— fork 省下的是那 80% 的表单 CRUD，而这**恰恰不是差异化，反而是包袱**；GSDbord 的价值在 **GSD 流程层 + 执行调度层**（§8.4），fork 在这两块**完全帮不上忙**，还得先花时间拆掉它原有的实体模型。GSD 的 phase / plan / wave 塞不进 Planka 的 board/list/card 三层。
2. **重型依赖** —— Plane 要 Postgres + Redis + 两个微服务；Planka 要 Postgres。违反 §9.2 依赖红线。
3. **License** —— Plane 是 AGPL-3.0。即便本项目全开源，混入其代码也会强制整个项目转 AGPL（§9.7）。

**该抄什么**：

- **代码**：**几乎没有**。唯一可读代码的候选是 Planka（MIT + React），限于组件划分与拖拽交互的局部参考
- **现成能力**：**OpenClaw 的 CLI backend 生态**（§8.4.2）—— 这才是 v0.8 真正的「白拿」，且比抄任何看板代码值钱
- **模型**：Plane 的实体划分（Projects / Cycles / Modules / Issues）——**只读文档**
- **设计**：Kanboard 的自动化动作模型、Linear 的键盘优先交互、Focalboard 的多视图切换

### 9.5 独立软件的架构预留（v0.4 新增，**M1 落地**）

原则：**现在花小钱，避免以后花大钱**。以下每条的「现在成本」多在小时量级，「以后补」多在周量级。

| # | 预留项 | 现在怎么做 | 不做的话以后要付什么 |
|---|--------|-----------|-------------------|
| 1 | **双对外契约：HTTP + MCP** | core 暴露 `createApp()`（HTTP，v0.7 前写作 `get_router()`）与一个 MCP server。**localhost HTTP 是主契约** | 每个新宿主都要重做一遍集成；agent 工具层 O(n) 重复 |
| 2 | ~~前端双产物~~ **单一静态站** | ⚠️ **v0.8 简化**：Hermes 退场后 IIFE 产物取消，Vite 只出 `web/dist` 一份，OpenClaw 与独立形态共用（§9.2、§10.5） | 独立版前端从零搭 |
| 3 | **清除宿主概念** | core 不得出现 `HERMES_HOME` 或 OpenClaw 路径；改用 `GSDBORD_HOME`，宿主路径由 adapter 注入 | 全局替换 + 配置迁移 |
| 4 | **身份模型** | 建最小 `users` 表；`assignee` 与 `events.actor` 存 user_id 而非自由字符串 | 每张表每个接口回填身份，历史数据无法追溯 |
| 5 | **鉴权抽象** | `AuthProvider` 接口：插件模式返回宿主当前用户，独立模式先返回单一本地用户 | 鉴权逻辑散落各处 |
| 6 | **DB 可移植** | SQL 保持 ANSI 风格，不用 SQLite 特有语法；连接层留 `Database` 抽象 | Postgres 迁移＝全量重写查询 |
| 7 | **全文检索隔离** | FTS5 **是 SQLite 独有的**，必须封在 `search` 模块接口后 | 换库时检索功能整体报废 |
| 8 | **正文存储抽象** | `BodyStore` 接口，默认 `MarkdownBodyStore`；将来可换 DB 存储 + MD 导出 | MD 路径硬编码渗入 service |
| 9 | **★ AgentRunner**（v0.8 权重大升） | 原意是「插件模式转发宿主 agent / 独立模式自带 LLM」。**v0.8 起它是执行调度层的核心接口**：`start / observe / reply / abort`，背后可换 OpenClaw CLI backend、Agent SDK、裸 spawn（§8.4.2、§19-B） | core 与宿主 agent API 焊死；**换执行后端等于重写调度层** |
| 10 | **配置来源抽象** | 配置读写走 `ConfigStore`，不直接读宿主目录 | 独立版无配置落点 |

> **前 3 项 M1 必做**（没有它们独立形态跑不起来）。4–10 项可在对应模块开工时落地，但**接口要在 M1 一并定义**，避免先写实现再补抽象。
>
> ⚠️ **v0.8 例外：第 9 项 `AgentRunner` 升为 M1 必做**。理由：执行调度层排 M2，但 §19-B（执行后端选哪个）还没定，而接口一旦留出来，B 就可以延后拍板；接口不留，M2 开工时会直接把 OpenClaw 焊进 orchestrator（§10.1 铁律 3）。

**独立形态最小交付**（M1 验收标准）：

```bash
gsdbord serve --port 8080        # 不依赖任何宿主
# 浏览器打开 http://127.0.0.1:8080 → 完整看板可用
```

### 9.6 License 与推广（v0.6 定案：**全开源，暂不商业收费**）

**决策：`LICENSE` 保持现有 MIT 不变。** 与 gsd-core（MIT）一致，生态最顺，双向取用无障碍。

v0.4 曾建议 Apache-2.0 + DCO，目的是保留商业化选项；既已确定暂不收费，那层复杂度不必背。

> 事实澄清：**MIT 不妨碍你以后卖自己的代码**。放弃的是排他性（别人也能拿去卖），不是收费权。

| 项 | 结论 |
|----|------|
| **开源协议** | **MIT**（保持不变） |
| 贡献者协议 | 可选。若在意日后改协议的权利，加 DCO（`Signed-off-by`）即可，门槛低 |
| **gsd-core 代码** | ✅ MIT，**可自由取用**，义务仅为保留版权声明（放 `THIRD-PARTY-NOTICES`） |
| **Plane / Wekan 代码** | ❌ AGPL-3.0，**一行不抄，只读文档**（§9.7）。即便自己全开源，混入 AGPL 也会强制整个项目转 AGPL |
| 其他参考项目 | 取用代码前先查协议（§9.3 表） |
| 商标 / 域名 | 建议尽早占位：GitHub org、PyPI、npm、域名 |

**推广（「打广告」）—— 可以，License 管代码分发条款，不管宣传。** 三条实际注意事项：

1. **署名义务** —— 取用 gsd-core 代码须保留其版权声明与 MIT 许可文本。
2. **不得暗示官方背书** —— MIT **不授予商标权**。可以说「GSD 流程的看板」「为 GSD 打造」「兼容 GSD」；**不要**做成看起来像 open-gsd 官方产品（勿用其 logo / 命名风格 / 自称 official）。
3. **最有效的推广是上游联动** —— gsd-core 有 CONTRIBUTING.md 与社区 Discord。开 issue 申请进生态列表 / 提 PR，比自行吆喝有效得多，也顺带把「非官方但被认可」的关系说清楚。

### 9.7 参考代码的合法边界（v0.5 新增）

**常见误解：「本项目也是开源的，抄过来没问题」——错。开源 ≠ 协议兼容。**

AGPL-3.0 是 copyleft（传染性），且方向单向：

- Apache-2.0 / MIT 代码 → 可以进 AGPL 项目 ✅
- **AGPL 代码 → 不能进 MIT / Apache 项目** ❌

复制 Plane 代码进 GSDbord 的后果不是「没事」，而是**整个 GSDbord 必须转为 AGPL-3.0**；随后网络条款生效——任何人将其作为网络服务提供都须公开整个作品源码。**§9.6 的商业版路线当场归零。**

**「看完自己重写」也不安全。** 行业认可的 clean room 要求：两组人、其中一组从未接触过源码、全部通信可审计。个人边看边写达不到该标准；在有充分接触史的前提下，「完全重写」不是有效抗辩。

风险分级（工程实践口径，非法律意见）：

| 做法 | 风险 | 是否可行 |
|------|------|---------|
| 读文档 / API 文档 / 数据模型说明 | 无 | ✅ |
| 读代码理解思路，隔期后以不同架构自行实现 | 低 | ⚠️ 可接受 |
| 对照代码逐段改写 | 高——构成派生作品 | ❌ |
| 复制粘贴 | 明确违规 | ❌ |

**操作规程**：

1. 需要抄代码时，**只从 MIT / Apache / BSD 项目抄**（§9.3 已标注），并保留原版权声明与 NOTICE。
2. AGPL 项目（Plane / Wekan）**只读文档**。若确已阅读其某模块代码，近期不要动 GSDbord 的同一模块。
3. 引入任何第三方片段时，在提交信息中注明来源与协议，便于日后审计。
4. **AI 生成代码同理**——若提示词中粘贴了 AGPL 代码，产出同样受污染。

### 9.8 gsd-core 内化方式（v0.6 定案：**vendor，不是外部依赖**）

**决策：把 gsd-core 的逻辑收进本仓库，GSDbord 独占状态写权。**

MIT 允许自由取用，因此不必把 gsd-core 当外部安装依赖。内化之后 GSDbord 是唯一写入者，**不存在与外部进程争抢 lockfile 的问题**。

**两种内化路径**：

| 路径 | 做法 | 成本 | 结论 |
|------|------|------|------|
| **B1 vendor TS 原样** | 复制到 `vendor/gsd-core/`，锁版本 | 低——复制即可，无需重写 | ✅ **采纳** |
| B2 移植为其他语言 | 重写阶段循环与编排 | 高——跨语言是重写不是复制；且从此 GSD 正确性由自己负责 | ❌ 不做 |

**⚠️ v0.8：若采纳 §9.1 的 TypeScript 决策，B1 大幅简化。**

| | Python core（v0.6 设想） | TS core（v0.8 建议） |
|---|---|---|
| 调用方式 | **subprocess** 起 `gsd-tools.cjs`，解析 stdout | **原生 import / require** |
| 状态传递 | 进程边界序列化，退出码语义要摸清 | 直接函数调用与返回值 |
| 错误处理 | 靠退出码 + stderr 猜 | 真异常，带栈 |
| 类型 | 无（跨进程） | **共享 TS 类型** |
| 调试 | 难 | 正常断点 |

⇒ **同语言把「集成」降级成「引用」。** 这是 §9.1 转 TS 的第 4 条论据，也是最省力的一条。

**⚠️ 一个必须先验证的关键假设（v0.8 提出）**：

> 本文档一直假定 gsd-core 是一个「可调用的库 / CLI」。但从其自述（「no database, no server, no external dependencies」、状态全在 `.planning/` 的 MD 里、五阶段靠 fresh-context 子 agent 推进）看，**它更可能主要是一套给 Claude Code 用的 slash commands + agent 定义 + 提示词模板，外加一个 `gsd-tools.cjs` 状态工具**。

若如此，「内化」的真实含义要改写：

| 组成 | 内化方式 |
|------|---------|
| `gsd-tools.cjs`（状态读写、lockfile） | ✅ 真的是库，直接 import（TS 下零成本） |
| `.claude/commands/gsd-*.md`（slash commands） | **不是代码，是提示词** —— GSDbord 要做的是把它们**安装到目标项目**，然后驱动 Claude CLI 执行（§8.4） |
| agent 定义（researcher / planner / plan-checker / executor / verifier） | 同上，是 subagent 定义文件 |
| 阶段循环编排逻辑 | **它跑在 Claude 的会话里，不在 gsd-core 的进程里** |

**如果这个判断成立，那么 §8.4 的执行调度层不是「GSD 内化」的补充，而恰恰是「GSD 内化」的唯一实现方式**——因为 GSD 循环本身就是由 agent 会话跑的，你不驱动会话就没有循环。这会让 §2 里「⑥ 与 M2 同期」的判断进一步加强为「⑥ 就是 M2」。

> **这是 M2 之前必须读源码确认的第一件事**（§9.8 待落实清单第 0 项）。判断错了会导致整个 M2 的设计方向错。

**vendor 的真实代价与对策**：

| 代价 | 对策 |
|------|------|
| 上游修复 / 改进不会自动流入 | 保持 vendored 副本为**干净子树**；在 `vendor/gsd-core/UPSTREAM` 记录上游 commit SHA 与同步日期，便于日后 diff / rebase |
| 本地改动与上游冲突 | 本地修改集中在薄适配层，尽量不改 vendored 文件本体；必须改时单独记录 patch |
| 署名义务（MIT） | 保留其 `LICENSE`；根目录加 `THIRD-PARTY-NOTICES`（§9.6） |

**语言结论（⚠️ v0.8 已变）**：

> v0.6 曾写「B1 下 GSD 逻辑以 TS 运行、Python 侧 subprocess 驱动，**Python core 的结论不变**」。
> 那个结论的前提是「Hermes 强制 Python」。前提已消失（§9.1），**gsd-core 是 TS 现在反过来成了转 TS 的论据之一**。

> **Hermes 列自 v0.8 起仅作历史对照**，不再是适配目标（§1.1）。

| 能力 | ~~Hermes~~（历史） | **OpenClaw**（唯一目标） | 关键差异 |
|------|--------|----------|---------|

| **★ CLI 后端注册** | 无 | **`api.registerCliBackend(...)`**，捆绑 `claude-cli` / codex / gemini | ✅ **v0.8 关键发现，执行调度层可复用**（§8.4.2） |
| **★ 会话持久化** | 无 | `--session-id` + resume；跨重启存活；历史入 `openclaw-agent.sqlite` | ✅ 不用自己写 |

| **★ 定时任务** | 无 | cron（多 agent 路由文档提及） | ✅ 每日巡检直接用（§8.5） |

**两条必须记住的官方约束（原文）**：

> 「a plugin bug can crash or destabilize the gateway; and a malicious native plugin is equivalent to arbitrary code execution inside the OpenClaw process」

⇒ OpenClaw 侧的 TS 薄壳必须**极其保守、错误全捕获**，不能把 Gateway 拖垮。

> 「External tabs require HTTPS/Tailscale Serve or a browser-trusted loopback origin; plain HTTP on a LAN host shows the secure-context error instead of mounting a panel」

⇒ `gsdbord serve` 跑在 `127.0.0.1` 属 trusted loopback，可用；**跨机访问必须上 HTTPS**。另：第三方 cookie 全面阻断时 gateway-protected tab 不可用。
gateway-protected tab 会下发 short-lived HttpOnly grant（scoped 到该插件与 route root），使 sandboxed frame 无需复制 Gateway bearer token。

**结论：能做「超大插件」，但形态与 Hermes 不同。** iframe 模式反而对 GSDbord 有利——`dist/standalone/`（§9.5-2）可直接复用，无需为 OpenClaw 重写前端。代价是 Hermes 那份 IIFE 不可跨宿主复用（§10.5）。

### 10.4 宿主矩阵与适配成本（⚠️ v0.8 重排）

| 宿主 | 后端形态 | UI 形态 | 增量成本 | 状态 |
|------|---------|---------|---------|------|
| **OpenClaw** | **in-process TS 插件** + `registerHttpRoute` | sandboxed frame 加载 `web/dist` | — | ★ **M1，唯一在做** |
| **独立应用** | `gsdbord serve` | 同一份 `web/dist` | **近乎零** —— 与 OpenClaw 共用前端和 app | M1（同期） |
| **Codex / Claude Code / Cursor** | 无需后端 UI | 无 UI，纯工具 | **低——MCP 一次实现全覆盖** | M4 |
| **VS Code** | **扩展内 in-process**（转 TS 后不再需要 sidecar） | Webview 加载 `web/dist` | **低**（转 TS 前是「中」） | M5+ |
| ~~Hermes~~ | ~~in-process Python~~ | ~~IIFE 注入~~ | — | ❌ **v0.8 退场**（§1.1） |
| piagent / workbuddy | 未知 | 未知 | 待调研 | 未评估 |

**转 TS 对本表的影响（§9.1 论据 6 的具体化）**：

> v0.7 时 VS Code 是「唯一需要新增运行形态的宿主」，因为扩展宿主是 Node，跑不了 Python，必须 sidecar：扩展 spawn 一个 Python 子进程、管生命周期、要求用户装 Python 或每平台打二进制。
> **转 TS 后这一整套消失**——core 直接在扩展进程内 `import`。原来记在 §15 的「VS Code 的 Python 分发」风险随之作废。

**若 §19-A 决定留 Python**，则以下代价重新生效并且**加倍**（因为现在连 OpenClaw 都要 sidecar 了）：

| 代价 | 影响面 |
|------|-------|
| 要求用户装 Python | **OpenClaw + VS Code 两个宿主**（v0.7 时只有 VS Code） |
| 进程生命周期管理（启停 / 端口冲突 / 崩溃重启） | 每个宿主写一遍 |
| 用不上 `registerCliBackend` | 执行调度层（§8.4）自己造 |
| 打平台二进制（PyInstaller / Nuitka） | 每平台一份，实打实的工作量 |

> **反面判断（v0.8 更新）**：v0.7 曾写「若 VS Code 是主战场，TS 才是正确选择；但 Hermes 强制 Python，选 TS 只会把 sidecar 问题镜像过去」。
> **Hermes 没了，镜像的另一端也没了。** 现在所有已知宿主（OpenClaw / VS Code / 独立）都是 Node 友好或语言中立的，**没有任何一个宿主要求 Python**。这是 §9.1 建议转 TS 的最终依据。

### 10.5 前端策略：**只有一种形态**（v0.8 定案，甲乙之争终结）

v0.7 摆了两条路线待拍板：甲（Hermes 原生 IIFE）/ 乙（统一 standalone + iframe 薄壳）。**Hermes 退场后甲不存在了，乙自动成为唯一路线，这个决策已消解。**

| 宿主 | UI 机制 | 复用同一份前端 |
|------|---------|-----------------|
| **OpenClaw** | sandboxed frame 加载插件 HTTP 路由 | ✅ |
| VS Code | Webview 加载 | ✅ |
| 独立应用 | 直接就是网页 | ✅ 原生 |
| ~~Hermes~~ | ~~IIFE 注入宿主 SDK~~ | ❌ 已退场 |

⇒ **`web/dist` 是唯一前端产物，同时是 OpenClaw 插件的前端本体。** 不再出双产物，IIFE 那一路彻底取消（§9.2）。

**净收益**（相比 v0.7 的甲乙纠结）：

- 前端只有一份，不存在「哪个宿主视觉不一致」的问题
- 不再受宿主 SDK 的组件集约束——想用什么 UI 库自己定
- **代价是失去 Hermes SDK 白送的 React + shadcn**，前端得自己搭构建链（§9.2 已记账，中低）

**唯一遗留的形态未知：iframe 里的 API 怎么连**（→ §10.3-8）：

| 若 CSP 允许连 `127.0.0.1:<port>` | 若不允许 |
|--------------------------------|---------|
| adapter ≈ **20 行**：注册 tab，指向 `gsdbord serve` 的地址 | adapter 要**经 `api.registerHttpRoute` 反代**全部 API + 静态资源 |
| 前端直连后端 | 前端只能走宿主路由，多一跳 |
| WebSocket 直连 | WebSocket 也要反代（§10.3-7） |

> 两种都能做，差别是 adapter 的厚度。**但 §8.4 的实时会话事件推送对这一项敏感**——若 WebSocket 反代不通，实时观察就得退化成轮询。这是把第 8 项列为 M1 第 0 步实测的原因。

## 11. 模块⑤ 度量体系

「科学度量」要落到具体指标，否则是空话。全部从 `events` 表现算，不做单独统计表（数据量级足够）。

| 指标 | 定义 | 用途 |
|------|------|------|
| **燃尽图** | 迭代剩余点数 / 天 | 迭代健康度 |
| **累积流图 CFD** | 各状态工作项数 / 天 | 识别瓶颈环节 |
| **周期时间 Cycle Time** | `doing` → `done` 耗时 | 交付效率 |
| **前置时间 Lead Time** | 创建 → `done` 耗时 | 端到端响应速度 |
| **吞吐量 Throughput** | 每迭代完成项数 | 容量基线 |
| **速率 Velocity** | 每迭代完成点数 | 迭代规划输入（§7 容量校验） |
| **缺陷密度** | bug 数 / 完成故事点 | 质量 |
| **缺陷逃逸率** | 上线后发现 bug / 总 bug | 测试有效性 |
| **阻塞时长** | `blocked` 累计停留 | 协作卡点 |
| **需求交付周期** | `inbox` → `done` | 需求管理全景 |
| **范围变更率** | 迭代中途增删项 / 承诺项 | 计划质量（§7） |

**GSD 专属指标（v0.6 新增，其他看板给不出的）**：

| 指标 | 定义 | 用途 |
|------|------|------|
| **阶段停留分布** | 各 GSD 阶段耗时占比 | 看瓶颈在 Discuss（想不清）还是 Execute（做不完） |
| **Verify 返工率** | Verify → Execute 回环次数 / phase 数 | **最有价值的一个**：直接反映 Plan 质量 |
| **Plan 通过率** | plan-checker 一次通过 / 总计划数 | 规划成熟度 |
| **Wave 并行度** | 平均每 wave 的 plan 数 | 拆解粒度是否合理；并行度低说明依赖过密 |
| **Phase 交付周期** | Discuss 起 → Ship 止 | GSD 循环的端到端速度 |
| **上下文重置次数** | 每 phase 的 session 边界数 | 是否频繁被 context rot 打断 |
| **人机操作比** | `events.actor` 中 agent 与人的比例 | AI 实际承担了多少（§12.5） |

**执行调度指标（v0.8 新增，来自 `runs` / `run_events`，§8.4.4）**：

| 指标 | 定义 | 用途 |
|------|------|------|
| **一次成功率** | `done` 的 run / 总 run | 上下文包（§8.4.5）组装得好不好 |
| **人工介入率** | 进过 `awaiting_human` 的 run / 总 run | **调度层的核心 KPI**：目标是让它降下来，但不是降到 0 |
| **平均等人时长** | `awaiting_human` → 人响应的耗时 | 人是不是瓶颈；巡检（§8.5）该多久跑一次 |
| **介入原因分布** | 按 §8.4.3 的触发条件分类 | 定位改进点：是提问多、还是权限卡、还是 Verify 老失败 |
| **会话成本** | token / 时长，按 phase 与 work_item 汇总 | 预算与 ROI |
| **中止率** | `aborted` / 总 run | 跑飞的频率 |
| **并发实际值** | 同时 running 的 run 数分布 | `max_concurrent_runs` 该调大还是调小（§8.4.3） |

> 这些指标的原始数据来自 `.planning/`、`STATE.md` 与 `runs` 表，但**时间序列必须由 GSDbord 自己按天快照**——`.planning/` 只存当前状态（§12.1 铁律 3）。

> 度量红线：**不做人效排名、不按人统计产出**。指标用于改进流程，不用于考核个人。

## 12. 数据设计

### 12.1 数据真相（⚠️ v0.6 **调整**：按实体分权，不再一刀切）

**旧决策（v0.1–v0.5）：SQLite 是唯一流程真相，MD 只是正文。** GSD 内化后这条不够用了——GSD 产物是 agent 要读、Git 要版本化的文件，不能降级为「SQLite 的导出」。

**但也不必反过来一刀切。** gsd-core 已 vendor 进本仓库（§9.8），GSDbord 是唯一写入者，不存在争抢，因此可以**按实体划分真相归属**：

| 实体 | 真相在哪 | 理由 |
|------|---------|------|
| **GSD 产物**：`PROJECT.md`、`REQUIREMENTS.md`、`ROADMAP.md`、`STATE.md`、`phases/**` | **文件**（`.planning/` 兼容布局） | agent 要直接读；Git 要版本化与合并；这是 v0.1 就定的差异化 |
| **GSDbord 独有**：users、assignee、bug、iteration、容量、RICE、links、**度量历史** | **SQLite** | 关系型、需组合查询；**GSD 根本没有这些的文件格式**，硬塞进 MD 是自找麻烦 |
| **会话账本**（v0.8）：`runs`、`run_events` | **SQLite** | 跨会话跨项目才能算的东西；**transcript 全文不存**，只存 `host_session_id` 指针（§8.4.4） |
| **复盘档**（v0.8）：`TIMELINE.md`、`HANDOFF.md` | **文件**（phase 目录下 `runs/`） | 要跟着 phase 一起 Git 版本化、要能被 agent 读；但**不改上游既有文件格式**（§8.6，放置位置待实测 §10.3-14） |

**铁律**：

1. **保持 `.planning/` 格式兼容**，即便逻辑已内化。收益：用户既有的 GSD 项目可直接被读取（天然的采纳入口），且与官方 gsd-core 双向互操作。
2. **写 GSD 产物一律经 vendored 的 `gsd-tools.cjs`**，不自己拼 MD —— 免费获得其 `STATE.md.lock` 原子写语义。
3. **文件侧的投影必须可重建** —— `gsdbord reindex` 能从 `.planning/` 重算 SQLite 中所有 GSD 派生列。
4. **SQLite 中的独有实体是原生数据，不可重建，须备份**（尤其 `metric_snapshots`：`.planning/` 只存当前状态，不存时间序列，CFD / 燃尽全靠按天快照）。
5. Git 跟 `.planning/` 与代码，**不跟 SQLite**（`.gitignore` 加 `gsdbord.db*`）。
6. **仍要假设文件会被外部改动** —— 用户可能同时装着官方 gsd-core，或手工编辑 MD。需变更检测（§9.8-5）。

> 这条调整现在改很便宜（SQLite 里还没有真实数据），堆了数据再改会痛。**M2 落地前必须完成。**

### 12.5 身份模型与可移植性（v0.4 新增）

**身份**——当前 `assignee` 是自由字符串（`cards.assignee TEXT`），独立软件形态下站不住：

| 项 | 做法 |
|----|------|
| `users` 表 | 最小字段：`id / handle / display_name / email / source / active` |
| `source` | `local`（独立模式自建）/ `hermes` / `openclaw`（宿主身份映射） |
| `work_items.assignee` | 改存 `user_id`，外键到 `users` |
| `events.actor` | 存 `user_id`；agent 操作用保留 id `agent:<name>` 以区分人机 |
| 权限 | **本阶段不做**。只建身份，不建角色与规则（§1.5 已降级为「暂缓但预留」） |

> 人机可区分是 AI-native 产品的必需品：度量（§11）里必须能回答「哪些流转是 agent 做的」。

**可移植性**——终局若要支持团队部署，SQLite 会成为瓶颈（§15 已列）。现在的低成本对冲：

- SQL 写 ANSI 风格，避开 SQLite 特有语法（`INSERT OR REPLACE`、隐式类型转换等）
- 时间统一存 ISO-8601 UTC 字符串（已是现状，`db.py:_now()`），不用 SQLite 日期函数
- 布尔用 `INTEGER 0/1`（已是现状），迁移时映射
- **FTS5 是 SQLite 独有**，封在 `search.py` 后（§9.5-7），Postgres 时换 `tsvector`
- JSON 列（`labels`、`extra_json`）：SQLite 存 TEXT，Postgres 可换 `jsonb`，读写都走同一序列化函数

> 明确不做的：不引 ORM 来「换库更容易」。表少、查询简单，手写 SQL + 一层 `Database` 抽象足够，引 SQLAlchemy 反而增加与宿主的依赖冲突风险（§9.1）。

## 15. 风险与取舍

| 风险 | 影响 | 应对 |
|------|------|------|
| **状态写入竞态** | 用户同时装了官方 gsd-core 或手工改 MD → 与 GSDbord 冲突 | 写 GSD 产物一律经 vendored `gsd-tools.cjs`（拿到 `STATE.md.lock` 语义）；加外部变更检测（§9.8-5） |
| **vendored 副本腐化** | 上游修复不流入，本地改动与上游冲突，日后无法同步 | 保持干净子树 + `vendor/gsd-core/UPSTREAM` 记录 commit SHA；改动集中在薄适配层（§9.8） |
| **自担 GSD 正确性** | 内化后 GSD 逻辑的 bug 变成自己的 bug | 走 B1（vendor 原样）而非 B2（重写），不引入自造的行为偏差 |
| **格式兼容性丢失** | 私自扩展 `.planning/` 格式 → 与官方 GSD 互不相容，失去采纳入口 | 铁律：不往 `.planning/` 写自有字段，GSDbord 独有数据进 SQLite（§12.1、§12.3） |
| **宿主耦合渗入 core** | 独立软件形态拆不出来，等于重写 | core 内禁用宿主名词；CI 加 grep 检查（§10.1 铁律 2） |
| **两种形态分叉** | 插件版和独立版行为不一致，维护量翻倍 | 同一个 `createApp()` + 同一份 `web/dist`；M1 起两种形态都自测。**v0.8 后风险大降**：OpenClaw 加载的就是独立形态那个 URL，前端不可能分叉 |
| **范围膨胀** | 对标 TAPD 做不完，烂尾 | §1.5 不做清单是硬约束；每个 M 只做一层 |
| **前端复杂度失控** | 六个模块的 UI 工作量；v0.8 起**没有可抄的同构源**（§9.9 作废） | Vite + React 从 M1 就上（§9.2）；shadcn 复制式拿组件；dnd-kit 接拖拽；先只做看板视图，表格/路线图排 M3 |
| ~~OpenClaw 无法复用 Hermes IIFE~~ | ~~以为抄完官方 kanban 就跨宿主了~~ | ✅ **v0.8 消解**：Hermes 退场，前端只有一种形态（§10.5） |
| **OpenClaw sandboxed frame 限制未实测** | 若不允许连 `127.0.0.1` 其他端口，adapter 要多写反向代理；**WebSocket 若不通，执行调度的实时观察退化成轮询** | §10.3-8 列为 M1 第 0 步必测项 |
| **插件搞崩 OpenClaw Gateway** | 官方明示插件 in-process 无沙箱，等同任意代码执行 | 插件壳写得极保守、错误全捕获、不在壳里做业务（§10.2）；**执行调度的子进程必须与 Gateway 生命周期解耦**——不能因为 Gateway 重启就丢会话 |
| **⑥ 执行调度：agent 跑飞** | 无人值守时 agent 改错文件、乱提交、装依赖搞坏环境 | 只有 Execute 阶段可放手（§8.4.1）；`awaiting_human` 永不自动跨过；权限白名单；**Git 是最后防线**——run 前记录 HEAD，出事可回退 |
| **⑥ 同 repo 并发写互踩** | 同 wave 的 plan 并行执行，改同一批文件 | wave 隔离的是上下文不是文件系统（§8.4.3）。**C1 串行化起步**，C2 worktree 隔离排 M3 |
| **⑥ 依赖 OpenClaw 生态被上游改动打破** | `registerCliBackend` / cli-backends 配置项变更 → 执行层报废 | `AgentRunner` 接口隔离（§10.1 铁律 3）；保留「自己 spawn」的退路实现；在 manifest 声明兼容版本 |
| **⑥ `-p` 模式不能实时打断** | 跑飞了只能等它跑完或强杀，无法边跑边纠 | 接管路径（`claude --resume`）+ abort；真需要边跑边引导时上 Agent SDK 长驻会话（§8.4.2 增强路径，M4） |
| **⑥ Claude CLI 版本漂移** | CLI 参数/输出格式变更 → 流式解析失效 | 靠 OpenClaw 的 `jsonlDialect` 吸收（这本身是复用生态的收益）；自己 spawn 的退路要锁 CLI 版本 |
| **⑥ 巡检变噪音** | 每天一堆卡没人看，最后全忽略 | 只对 `watched` 项目开；无事不建卡；报告合并成一张；同问题不重复提醒（§8.5） |
| **⑥ 会话成本失控** | 无人值守跑一夜烧掉大量 token | `runs` 记 token 与成本；设单 run 与日预算阈值，超限转 `awaiting_human`（§8.4.3） |
| **MD / SQLite 双写不一致** | 数据可信度崩塌 | 单一写入口（`service.py`）；SQLite 为准；提供 `gsdbord doctor` 校验修复 |
| **SQLite 并发** | 独立软件做团队部署时，多人写会成瓶颈 | 已开 WAL；当前定位单机；**SQL 保持 Postgres 可移植**作为对冲（§12.5） |
| **流程管理过度约束** | 团队被卡死后弃用 | 准入准出检查器**默认全关**，按需开启 |
| **AI 建议不可信** | 用户不敢用 | 所有 AI 写操作默认 `dry_run`；优先级/范围类决策强制人确认 |
| **宿主生态获客不及预期** | 冷启动失败 | 独立形态 M1 就可用，不把全部赌注押在插件市场 |
| **AGPL 代码污染** | 抄了 Plane 代码 → 全项目被迫转 AGPL，商业版归零 | ⚠️ 只从 MIT/Apache 项目取用代码；AGPL 项目只读文档（§9.7） |
| **宿主越加越多，适配成本 O(n)** | 每家写一套 agent tools + UI，维护崩溃 | 契约收敛为 localhost HTTP + MCP，宿主侧只留薄壳（§9.5-1、§10.4） |
| **Python 分发**（⚠️ v0.8 影响面扩大） | 用户没装 Python 就用不了。**v0.7 只影响 VS Code，现在影响 OpenClaw 本身**（npm 包要求外部 Python 环境） | ✅ **转 TS 则此风险归零**（§19-A）；留 Python 则要求 3.10+ 并考虑 PyInstaller 打平台二进制 |
| **转语言的返工风险**（v0.8 新增） | 转 TS 要重写现有 ~400 行 | 量小、且是最机械的 CRUD；**表结构、状态机、§9.5 十项预留、§8.4 调度设计全部原样成立**，返工仅限实现（§9.1 末） |
| **与宿主原生看板重叠**（OpenClaw Workboard） | 用户不知道用哪个 | 独立库独立 Tab；定位差异写进 README：**Workboard 是任务清单，GSDbord 是 GSD 流程 + 执行调度** |
| **插件 API 随宿主升级破坏** | 装不上 | manifest 声明兼容版本；CI 冒烟 |
| **Plane 已是 AI-native + MCP** | 差异化被抹平 | 差异点押在 local-first + 宿主内嵌 + MD 可读，而非功能数量 |

## 19. 待决清单（v0.8 新增，★ 全部阻塞开工）

> 放在文末是为了好找。**这三项定不下来就不该动代码**——它们各自影响的不是一个模块，而是整个实现的写法。

### A. 语言：转 TypeScript 还是留 Python？（**最优先**）

| | 转 TS（建议） | 留 Python + sidecar |
|---|---|---|
| OpenClaw 插件 | ✅ 原生 | 必须外套 TS 壳 + 用户自备 Python 环境 |
| npm 分发 | ✅ `npm i` | ❌ **采纳率杀手** |
| `registerCliBackend`（§8.4.2） | ✅ 能用 | ❌ 执行调度自己造 |
| gsd-core | ✅ 原生 import | subprocess |
| 前后端类型 | ✅ 共享一份 Zod | 两套 |
| VS Code | ✅ in-process | sidecar |
| 现有代码 | 重写 ~400 行（几小时） | ✅ 保留 |

**建议转 TS。** 唯一未知变量是**你写 TS/Node 的熟悉度**——若生疏，整个项目每行都慢，那是唯一值得推翻上表的理由。详见 §9.1。

> 依赖此决策的章节：§9.1、§9.2、§9.8、§10.1、§10.4、§16。

### B. 执行后端：OpenClaw 内建 vs 自建长驻会话

| | B1 OpenClaw `claude-cli` 后端（建议默认） | B2 Agent SDK 长驻会话 |
|---|---|---|
| 会话持久化 / resume | ✅ 现成 | 自己写 |
| MCP 桥 + skills 透传 | ✅ 现成（有坑，§8.4.5） | 自己写 |
| 流式解析 | ✅ 现成 | 自己写 |
| **实时打断** | ❌ | ✅ |
| **权限请求上抛** | ❌（须预设 permission-mode） | ✅ |
| 人工接管 | ✅ `claude --resume`（几乎免费） | ✅ |

**建议：B1 做默认路径 + 真终端接管，B2 排 M4 作为增强。** 两者藏在 `AgentRunner` 接口后面（§10.1 铁律 3），所以这个决策**可以延后**，但要现在就把接口留出来。

**子问题（依赖 §10.3-11 实测）**：插件能否程序化起会话？

- 若能 → GSDbord 主动排队起会话（可控性好，符合「调度层」定位）
- 若不能 → 只能「GSDbord 出 MCP 工具 + 状态，让 OpenClaw 的 orchestrator agent 自己调 `sessions_spawn`」。更 agent-native，但队列与并发由 agent 判断，可控性差
- 兜底 → 绕开 OpenClaw 会话层，自己 spawn Claude CLI（重复生态，但完全可控）
